# Agent 生产工作台：基础生产功能补充 · 原型 0.3

日期：2026-09-20。仍为原型评审，不改正式程序。对外名称统一为 Agent，不展示技能包作者和版本品牌。

## 修正原因

上一版只以说明文字提到基础服务商设置，实际没有密钥表单；还把出图/视频并发放进默认关闭的高级功能包。这样“简化界面”变成了“找不到生产必需配置”。本次将生产必需配置与可选高级工具明确分开。

所有已接入服务商和必要凭据形式应在正式版保留，不只支持这 3 家样例。界面按服务商声明生成字段：通用 API Key、1K/4K 分组、视频专用 Key、需要的账号组合与多账号配额。只有原 Studio 内部文字模型的密钥和并发退出新流程。

已有 Base URL 与配置应迁移保留；密钥留空表示不改，清空需明确操作。是否配置与实际鉴权成功是两种状态。按账号数量限制并发的服务商，还必须遵守实际账号配额，不能被手填数字突破。

## 并发与线程的口径

- **批内并发**：本项目这一类任务最多起多少个 worker。
- **服务商上限**：同一家服务商在多个项目、多个批次之间共享。
- **全局总上限**：所有项目的图片与视频在途任务合计，不按项目各算一份。
- **当前线程**：本程序实际线程总数，包含生产以外的线程，不能直接当成正在生产的任务数。
- **建议并发**：建议同时生产的任务数，结合实测内存变化、服务商限流/耗时与账号配额；它不是操作系统线程数的上限。没有足够证据时显示待采样。

单行可占用额度不高于批内并发、对应服务商上限和全局上限中的最小值；多行共享额度，不能将各行显示的理论上限相加。实际执行还取决于依赖、待办数量和已占用槽位。

调低上限只影响后续提交，不撤回在途任务。因此短时间出现“在途 7 / 新上限 6”是可解释的状态，应让新任务等待，而不是伪造在途数立即降到 6。

## 旧程序复用依据与实施注意

- `core/executor.py` 的 `Gate` 及批次 `ThreadPoolExecutor` 已有批内、服务商、全局三层控制；正式改造沿用跨项目共享配额语义。
- `core/resources.py` 的 `snapshot()` 已返回 `threads`、CPU、系统内存和进程内存；`advise()` 已区分样本不足与服务商限流。
- `web/index.html` 的 `renderProviders()` 已按服务商区分 Key 字段；`gText`/`tickRes()` 已展示在途状态和资源建议。原型简化不能把这些能力删掉。
- `server/app.py` 的 `/api/resources` 目前仍采集文字模型闸门/峰值。正式 Agent 模式移除内部文字分析后，需要把采样和建议口径改成图片/视频生产，不混入历史文字分析峰值。
- 密钥只由 Studio 的服务商配置管理，不写入 Agent 任务模板、项目材料、错误修订包或共享原型。
- 轮询、结果取回与文件校验继续保留；服务商完成、下载完成、文件可用分别计状态，失败重取不应默认为重新计费生成。

# ChatGPT 制图桥接与多机器队列

日期：2026-10-19

起因：用户原话「我希望是一个自动化类似于中转站API那种我中间搭一个桥梁然后chatGPT能自己去吃我的任务列表然后完成任务还需要适配多机器同时提交任务」。

## 我查到的

当前 Studio 用 Provider 直接提交生成请求，并没有让 ChatGPT 领取任务的中心队列、执行节点和成品回传接口。只增加一个服务商地址不能让普通聊天会话自动监听队列。

- `core/providers/base.py` 的 ImageTask / Provider 是图片任务公共入口，参考图顺序就是 Image 1..N。桥接适配应覆盖所有进入该入口的出图任务，不只覆盖资产图或一个生产体系。
- `core/submitted.py` 的 remember / current_record / new_attempt 已支持保存任务 ID、重启续查和防止已有 ID 时自动重提。桥接服务应沿用该规则，同时补上提交响应丢失前的幂等标识。
- `server/agent_api.py` 的 /api/agent/manual 是人工放图入口；自动桥接应通过 Provider 下载、校验并保存到原任务输出路径，不依赖人工文件名匹配。
- 官方说明 ChatGPT 可通过工具/插件访问外部服务，支持相应计划中的定时任务；这不等于已验证内置图像生成能够在用户实际客户端中无人值守领取并回传。必须先做真实单任务验证。
- 官方 Sign in with ChatGPT 的计划用量调用目前明确不支持 image generation，不能将该登录流程当作图像接口。普通网页/桌面聊天也不能仅凭队列 URL 就持续自动运行。

官方依据（2026-10-19 核对）：
- https://developers.openai.com/siwc/token-sharing-open-source/preview-limitations
- https://learn.chatgpt.com/docs/image-generation
- https://learn.chatgpt.com/docs/automations
- https://learn.chatgpt.com/docs/extend/mcp

## 建议的交付范围（待确认执行端）

1. 宝塔 Linux 上独立运行桥接 API：账号/机器鉴权、持久队列、任务查询、参考图和结果存储、管理页。与现有登录服务分进程部署，不替换已有认证程序。
2. Studio 桥接服务商外挂：上传提示词和有序参考图，立即取得 task_id，轮询状态并取回图片；断线重启继续查原 ID。
3. ChatGPT 执行端：通过 MCP/插件或经实际验证的界面适配领取任务，调用可用的内置制图能力，上传真实图片后才确认成功。没有可用执行端时任务保持排队，不能报虚假成功。桌面工具/插件方案是候选，尚未证明适用于用户的具体客户端。
4. 多机规则：服务端原子领取、领取凭证与版本、心跳、每执行账号独立并发、提交账号/机器/项目/任务版本关联；重复 HTTP 请求返回同一个任务。增加提交机器不自动增加出图并发。
5. 中断规则：尚未开始生成的领取可安全回收；已经开始或是否开始不明时标记待恢复，禁止仅因租约超时再生成。结果上传可以幂等重试；明确失败显示失败，用户下次提交可新建尝试。
6. 已生成图片保留真实格式并校验，不静默声称精确 4K/尺寸或参考图数量均受支持；能力需按实际执行端验证。下游任务仍由 Studio 按依赖就绪后提交。

第一阶段验收：一条带参考图任务从 Studio 提交，经真实 ChatGPT 生成，自动回填；再验证两台提交端并发、重发提交、执行端中断后的不重复生成。完整链路验证前不承诺网页无人值守或所有账号通用。

## 要用户确定的运行条件

### 1. 出图执行端先适配哪个？

- A（推荐先验证）：能使用内置生图和工具/插件的 ChatGPT 桌面版。便于下载、保存和回传文件；需要实际客户端验证及执行电脑持续在线。
- B：ChatGPT 网页版。需要浏览器保持登录；网页工具能力、自动触发和结果回传均需验证，页面变化会增加维护成本。
- C：两者都能接受。先验证当前账号可跑通的一个入口，再决定适配，不同时建设两套执行器。

### 2. 多台 Studio 的任务由谁的 ChatGPT 执行？

- A（推荐，符合集中桥接）：由用户管理的指定出图电脑统一处理，其他机器只负责提交和取回。集中管理队列与额度；执行能力取决于这些出图电脑及账号实际额度。
- B：每个使用者在自己的出图电脑登录自己的 ChatGPT，只处理授权给自己的任务。账号隔离明确，但每个执行端都要安装和维护。

## D:\DA 接入核对

已有 Flask / MySQL、账号权限、Flow Token、Worker 注册、领取 / 心跳 / 完成接口，以及 R2 存储（模块仍名为 cos_client）。`tools/flow_runner` 和浏览器扩展均使用这套 Flow 任务池。

关键差异：`app/services/db.py` 的 FlowTaskService.lease_one 和 reclaim_expired_leases 会回收过期 leased 任务，批次还有自动重试逻辑；旧 Worker 的领取请求没有执行引擎过滤。直接共用旧任务行会导致 ChatGPT 任务被 Flow Worker 取走，或 ChatGPT 仍在出图时重复派发。

实施边界：在 DA 内增加独立 ChatGPT 通道，复用账号权限、MySQL 连接和 R2 存储；旧 Flow 调度不变。Studio 通过外挂对接。ChatGPT 桌面端仍需要实际内置生图与工具能力验证，不以普通 HTTP 请求或登录令牌冒充桌面生图。

## 本次交付

DA 中新增 cg_tokens / cg_jobs / cg_files、受账号权限与 Token 角色保护的队列 API，以及管理页。提交请求在 Studio 发出前持久化幂等编号和参数快照；执行机在领取和开工前分别记录凭证和意图。尚未开工的任务可回收，已经开工的任务保持原 ID，结果回传可重试。明确失败后下一次生产才创建新尝试。

交付文件位于 `D:\DA\dist-chatgpt`：DA 服务端增量升级 ZIP、免装 Python 的 Windows 桌面执行包、Studio `da_chatgpt.py` 外挂。外挂通过所有图片任务共用的 Provider 入口工作，本次不重打 Studio EXE。执行包注册本地 MCP 并提供定时任务指令；只有实际桌面客户端具备内置生图、文件访问和调度能力才能无人值守。

为什么独立通道：原 Flow 按超时自动回收，而网页/桌面生成中断不等于服务端停止出图；共享任务池会误派给旧 Worker 或二次生成。现在任务开始后不因租约超时转派，恢复时只回填原结果，避免网络断开触发重复生成。

验证：DA 全量测试及真实 Studio 基类兼容测试共 26 passed；管理页浏览器操作与打包 EXE 的 MCP 握手通过。SQLite 事务适配测试不是生产 MySQL 实测。指定电脑的真实生成、实际 ChatGPT 调度、生产 R2/数据库与线上升级尚待部署验收；不能把包已生成说成整条生产链路已验收。

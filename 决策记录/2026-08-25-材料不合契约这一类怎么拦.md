# 材料不合契约这一类怎么拦

日期：2026-08-25
起因：用户原话 ——「同一个 key 出现两次的本质是 codex 没有正常按照你的需要给出」

## 我查到的

### 定性

上一轮我把「同 key 两条 → 静默覆盖」写成解析器的漏洞，**归类错了**。

机制是：`core/matimport.py` 的 `audit()` 只查材料**内部自不自洽**（引用链闭合、
编号连续、张数上限、段号连续），不查**材料是不是照契约产的**。同 key 两条内部
完全自洽 —— 于是验收 0 条问题，`build()` 建出 2 条任务却只落 1 份提示词文件
（`prompt_path` 按 key 算路径，第二条盖掉第一条），其中一条的提示词永远丢了。

所以这不是一个 bug，是**一整类**：「codex 没照契约产，而我没吭声」。
按这一类去查，现在的状态是：

| 拦得住 | 拦不住 |
|---|---|
| 坏的 JSON 行（记行号） | **key 重号** → 静默覆盖 |
| 缺 key / filename / prompt | **少给了** → 84 条只给 80，剩下 80 条内部自洽，一句话说不出来 |
| image_n 跳号、重号 | **prompt 是占位/残篇** →「同上」「略」非空，照样过 |
| 引用了没人产出的 key | **kind 认不出** → 既不是 image 也不是 video 时被判成 image |
| 集内 SEG 缺号 | **视频没有骨架** → `storyboard_refs` 空，到出片那一层才报「缺故事板」 |

### 「少给了」是这里最关键的一条

现在我**只能查内部自洽，查不出少产**。84 条给 80 条，剩下的引用链闭合、编号连续、
段号连续 —— 全绿。要能对账，材料里必须有一份 codex 自己的**申报**（共几条、图几条
片几条、几集、每集几段），拿申报和实际条数比才知道少了。契约里现在没有这一节。

### 范围

这一类的检查只有一处（`core/matimport.py::audit`），契约声明也只有一处
（`core/matspec.py::AUDIT`）。但**两处必须同改** —— 契约从代码生成的意义就是
「会被怎么查」和「实际怎么查」是同一份东西；只加检查不加声明，等于让 codex
在不知道规则的情况下被判不合格。

### 我不问、直接定的

- **绝不自动去重、绝不自动补号、绝不自动挑一条留下。** 自动兜过去正是这个项目
  最贵的那一类 bug（不报错，只是少了或者错了）。重号就是重号，报出来让它重产。

## 要你定的

### 1. 要不要让 codex 多产一份「申报头」

这是唯一能查出「少给了」的办法。

- **A（推荐）**：契约里加一节申报，材料第一行是一条 `{"kind":"manifest", ...}`，
  写明总条数、图/片各几条、共几集、每集几段。导入时拿它和实际条数对账，
  对不上直接不导。
  —— 好处：**「少产」变成响亮失败**，这是现在完全查不出来的一类。
  代价：codex 要多产一段；它自己申报错了（申报 84 实际 84 但本该 88）仍然查不出，
  这一条只能拦「申报和实物不一致」。
- **B**：不加申报，用项目设置里的集数和每段秒数反算预期条数来对账。
  —— 好处：不改契约，codex 那边零负担。
  代价：导入模式下用户很可能压根没填那些设置（它们本来是给 LLM 路径用的）；
  而且如果 codex 判定某一集只需要 3 段，按设置对账会**误报**，
  误报会让人学会忽略这道门。

我倾向 A。理由：B 的预期值来自程序的假设，A 的预期值来自生产者的承诺 ——
查「你有没有兑现你说的」比查「你符不符合我猜的」准，而且不会误报。

### 2. 有不合格的时候，整份不导还是导能导的

234 条里坏 3 条，让它重产整份 234 条很贵。

- **A（推荐）**：整份不导，但同时**导出一份「要重产的清单」**（只列坏的那几条
  和坏在哪）。你把清单丢给 codex，它只补这几条，补丁文件和原材料一起放进
  `00_生产材料/`，程序两份一起读、后来的覆盖同 key 的。
  —— 好处：不用重产整份，也不会出现「一半导进去了一半没有」的状态。
  代价：要做多文件读取和补丁覆盖（现在是单文件整份覆盖）。
- **B**：把合格的先导进去，坏的列出来，之后再补一次增量导入。
  —— 好处：能先出图，不空等。
  代价：`tasks.json` 会半真半假。而「这条做过没有」判据是**产物文件在不在** ——
  半份状态下你分不清「这条还没做」和「这条压根没导进来」，
  中间只要点一次一键跑到底，缺的那几条就静默地不存在了。

我倾向 A。理由：B 省下来的时间，会在「为什么少了 4 段而且没人报错」上还回去 ——
那正是我们花了一整周在修的那一类。

### 3. prompt 是不是残篇，要不要用启发式去查

查不全，但能抓住「整批简化」那种。

- **A（推荐）**：查，报 **warn 不 error**（不拦导入，只在导入结果里列出来）。
  两条判据：出现占位词（同上／同前／略／待补／TODO／…）；长度明显短于同类中位数
  （比如不到中位数的 30%）。
  —— 好处：codex 一次产 234 条超长输出，中途开始写「（同前）」是真实风险，
  而这一类**现在完全查不出**，出图那一刻会拿一段残缺提示词去出图，图也出来了，
  只是不对。代价：会有误报（真的很短的提示词被点名）。
- **B**：不查。残篇属于「验收根本查不到」，明确写在契约里靠 codex 自己保证。
  —— 好处：没有误报，警告栏不会长出噪音。
  代价：整批简化这种最贵的情况，要到看图才发现。

我倾向 A 且**只报 warn**。理由：这一条我没把握做到低误报，做成 error 会变成死路；
做成 warn 的话，误报的代价只是多看一行字。

## 怎么修的

### 一、申报头（第 1 题）

`core/matimport.py`：`MANIFEST` / `manifest_of()` / `units_of()`，
`_from_json` 单独认 `kind: "manifest"`，`_reconcile()` 拿申报和实物对账
（总条数、图片/视频条数、集数、每集段数）。

三处必须同时防住，缺一处申报头就会变成一条永远做不完的活：
`audit` / `build` / `summary` 入口全部先 `units_of()`。

**没有申报头只报 warn，不报 error。** 已经产出来的 md 老材料没有这一节，
判 error 就是把它变成死路 —— 而死路比漏检更糟。

对账的边界写进了契约：它查的是「你有没有兑现你自己说的」。
申报 84、实际 84、但本该 88 —— 这个查不出来，那是它自己的判断，程序无从知道。
不写清楚的话，「导入通过」会被当成「材料齐全」。

### 二、整份不导 + 告知（第 2 题）

`reproduce_request(units, issues)` 把不合格的点写成一份清单，按 code 分组。
`/api/material/import` 被拒时落到 `00_生产材料/要重产的清单.md` 并回传正文；
`/api/material/preview` 也回传，页面上有「复制」按钮和展开预览。

**清单里原本写了「补出来的和原材料一起放，一起导」—— 删掉了。**
`_read_material` 一次只读一个文件，程序不会合并两份。留着就是承诺一个
不存在的行为，而它失败的样子恰好是最糟的那种：补的那几条压根没进来，
而两份都「导过了」。现在写的是实际能做的：替换回原材料里再导一次。

### 三、不做残篇检查（第 3 题）

按你说的不加启发式。改成在**契约**和**要重产的清单**里各明写一句
「提示词正文必须完整可投喂，不要写『同上』『同前』『略』；
这一条程序查不了，残篇会一路跑到出图那一刻，图也出得来，只是不对」。

### 四、同一类里顺带补齐的（都在定性那张表的 ✗ 列里）

- **key 重号** → error。不去重、不补号、不挑一条留下。
- **filename 重号** → error。产物落同一个路径，而「做过没有」看产物在不在。
- **视频缺 `storyboard_refs`** → error。
- **kind 认不出** → 不建任务，`build` 返回 `skipped` 让人看见
  （`force` 压过验收时，这里是最后一道）。

契约那一侧（`core/matspec.py`）同步加了这五条声明 + 申报头一节 +
「程序查不了的，靠你保证」一节。**只加检查不加声明，等于让 codex
在不知道规则的情况下被判不合格。**

契约里的示例改成了**一份完全合格的最小材料**（申报头 + 故事板 + 人物 + 视频，
四行）：抄下来原样导入 0 条问题。测试直接断言这件事 ——
示例自己申报 3 条而实际 2 条、或者引了一个自己没产出的 key，
会教出同样的毛病来。

测试：`tests/test_material_import.py::ContractComplianceTests` 13 条，全量 1931 通过。

## 为什么会有这个问题

`audit()` 只查材料**内部自不自洽**（引用链闭合、编号连续、张数上限、段号连续），
不查**材料是不是照契约产的**。同 key 两条内部完全自洽 —— 于是验收 0 条问题，
`build()` 建出 2 条任务却只落 1 份提示词文件（`prompt_path` 按 key 算路径，
后一条盖掉前一条），其中一条任务读的是别人的提示词。

它能长期不被发现，是因为**每一步看起来都成功了**：验收绿、导入绿、
出图绿、任务标成功。错的只有画面，而画面要人去看。

更根上的原因是我把它归错了类。上一轮我当成解析器的漏洞，
准备一个症状补一条 audit。用户的一句话改了定性：
「同一个 key 出现两次的本质是 codex 没有正常按照你的需要给出」——
这是**一整类**（材料不合契约），不是一个 bug。按类去查才发现同一列里还站着
「少产了」「视频缺骨架」「kind 认不出」「filename 重号」四个，
其中「少产了」压根没有任何检查能碰到它。

## 修完能避免什么

以前这三种情况会一路跑到成片：

- **重号**：234 条导进去，出图全绿、任务全绿，某个人物的两张图里有一张
  用的是另一条的提示词。你要到看图才发现，而那时候钱已经花了。
  现在停在导入前，报出是哪个 key、在第几条和第几条。
- **少产**：申报 84 段、实际给 80 段。以前剩下 80 段引用链闭合、编号连续、
  段号连续 —— **全绿**，一路跑到拼接，成片短一截而拼接不会说话。
  现在停在导入前，报「EP05 的段数对不上：申报 4 段，实际 3 段」。
- **kind 认不出**：以前落到 `else` 分支变成一条资产图 —— 一条视频被当图片
  出掉，出得来、任务标成功，成片里少一段而没人报错。
  现在不建任务，并且在导入结果里列出来。

反过来也要说清**没有变好的**：残篇、引错了参考图、时间连不连得上，
这三件仍然要到看图看片才发现。契约里明写了，不假装能查。

# 追加（同日）：项目参数进契约 + 契约按体系分两份

起因：用户原话 ——「1、项目参数也写进契约但是是他给你的不能做任何的限制，
2、需要按照项目体系来给两份契约」

## 一、项目参数由材料申报，程序不拿它当限制

和申报头是同一个原则：查「你有没有兑现你自己说的」，不是「你符不符合我设的」。

申报头里多一个 `params`：集数、每集多少秒、每集几段、单段几秒、画幅、
出图尺寸、剧情节奏、字幕。程序只做三件事 —— 显示出来、当没写 `duration` /
`ratio` 那几条的默认值、拿 `segs_per_episode` 和实物对账。**不夹、不改、不拦。**

`build()` 里材料申报的参数**盖过项目参数**。反过来的失败样子很难看：
提示词按 20 秒写的，派出去的活是 15 秒，片子和提示词对不上而不报错。
但盖了要说出来 —— 导入结果里回 `used_params`，页面上写「材料自己申报的，
盖过了项目参数」。悄悄盖的话，「我明明设了 15 秒」这类问题永远查不到源头。

单条自己写的 `duration` 仍然最优先 —— 那是这一段的实际长度。

## 二、契约按体系出两份

`matspec.SYSTEMS` 分 v34 / v61，`render(limits, name, system)`。
导出时按项目的体系走，没开项目按这个包默认建的那一套；
文件名带体系（`生产材料契约_通用十二环节.md`），两份并存看得出哪份是哪套的。

差别不只是少一节：

- 通用十二环节**没有场景状态图**这一步。
- 通用十二环节自己只建六个资产目录（`core/stages._CAT_DIR`：人物身份/场景/
  道具/连续状态/群体/生物），造型、服饰、载具、特效那几类它没有。
  产了这套体系用不上，**而它还占着参考图的名额**。

契约里的家族前缀表是从 `matimport.out_path` 那张表来的，测试逐条断言
「契约说的落点就是实际落点」—— 说一套落一套是这里最贵的错。

## 三、顺带查出来的真 bug：视频落错目录

对照测试里发现的：契约要求视频的 key 是 `EP01-SEG01`（拼接按这个前缀挑本集
分段），而 `out_path` 按 key 里的家族前缀算落点 —— **那个形状里没有 `VIDEO`
前缀**，于是每一段视频都落进 `02_固定资产/其它资产/`。

表现出来是：出片全成功、任务全绿，而拼接在 `05_分段视频` 里一个文件都找不到，
报「这一集没有分段」。钱全花了，成片一段都没有。

改成 `kind == "video"` 就落 `05_分段视频/`，不看 key 长什么样。契约里也写明了
这一条，并把家族表里的 `VIDEO` 一行删掉 —— 留着会让人以为 key 里必须有它。

这个 bug 是「契约说的和程序做的对不上」那一类，而它能被抓到的唯一原因是
我把两套体系跑了一遍对照。**上一轮只跑单元测试没发现** ——
单元测试用的 key 都带长 ID（`PRJ_X__VIDEO_...`），恰好命中前缀。

测试：`PerSystemContractTests` 5 条、`DeclaredParamsTests` 7 条、
`VideoLandsInTheVideoFolderTests` 4 条；全量 1947 通过。

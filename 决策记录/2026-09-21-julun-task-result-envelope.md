# 巨轮视频终态兼容顶层响应，并保留失败原因与重试分类

日期：2026-09-21

起因：用户报告巨轮视频任务已完成却取不回视频，提供一个完成任务和两个失败任务，要求修复并说明失败任务如何处理。

## 定性与证据

巨轮接入依据旧响应 `{"code":"success","data":{...}}` 编写，`JulunProvider._poll` 只读 `data.status` 和 `data.result_url`。本次三个真实查询均为 HTTP 200，任务状态却在响应顶层；完成任务是 `completed`、进度仍为 95、结果地址非空，失败任务的原因在顶层 `error.message` / `error.code`。原解析把这些终态读成空值，继续等待至超时。旧测试只有 data 包装样本，所以没有暴露这个格式差异。

已完成任务的结果地址交给现有 `HttpSession.save_item`，约 11.77 秒下载 24,383,010 字节；ffmpeg 完整音视频解码成功，约 30.08 秒、720×1280。说明本次取不回的机制在状态解析，本次直接下载正常；不能据此推断服务商历史上所有下载都正常。

两个真实失败样本：

- `task_Nxpm…`：`video_generation_failed` / `video generation failed`。没有更具体原因，不能断言是审核、网络或余额问题。
- `task_jLg…`：`task_failed`，原文含肖像权保护与 `For likeness protection`，要求检查素材与账号条件。原样重发不能解决这一条件。

## 范围与处理

巨轮所有视频模型共享同一个 `_poll`，新 Agent 工作台与旧项目视频生产都调用此服务商实现。本次仅调整巨轮适配器及其测试，不改变任务依赖、LLM 工作流或其他服务商。

- 支持顶层任务状态与旧 data 包装，完成状态不要求进度等于 100；已知进行中状态仍继续查询。
- 保留旧版无结果地址时的 `/content` 下载路径，并将现有下载进度日志传给任务日志。
- 失败时立即停止轮询，保留错误原文、机器码和任务 ID。失败响应即使带旧结果地址，也不会下载。
- 一般生成失败沿用已有重试预算：Agent 工作台默认最多重试 2 次，即首次加两次重新提交；设为 0 时不重试。预算用尽写失败记录，不影响无关任务。
- 肖像保护拒绝标为单任务不可重试，停止原样重发，保留服务商说明，处理素材与账号条件后由用户手动重试。其他无关任务继续。
- 移除异常里无条件声称“失败不扣费、自动原路退回”的文案。查询响应没有提供退款凭证，计费以服务商记录为准。

本次真实接口仅查询既有任务，并取回先前的完成视频；两个失败任务未实际重新生成。Key 未写入配置、测试或本记录。此修复不自动恢复旧任务、不自动重跑历史失败任务，也没有重新打包 EXE。

## 验证

新增 19 项回归，先在旧代码复现：15 项失败、4 项通过。修复后巨轮相关 69 项全部通过，覆盖新旧响应、95% 完成、进行中不提前下载、无地址回退、原始失败原因与错误码、肖像拒绝、真实执行器重试次数与失败落盘。

将三个已保存的真实响应交给修复后的解析器离线回放：每个只查询一次即识别终态；完成任务返回原结果地址，一般失败为 retryable，肖像保护失败为 task_fatal。未使用真实服务生成测试视频。

全量回归：2611 项全部通过，耗时 360.14 秒。日志：`outputs/julun-full-tests-20260921.log`。三个真实响应的离线回放：`outputs/julun-diagnosis-20260921/fixed-parser-replay.json`。

## 修完能避免什么

巨轮把视频任务的状态改为顶层返回时，完成任务会开始下载，失败任务会及时显示实际原因；不会再把已知终态当成空状态等待至超时。一般失败遵循已有重试上限，肖像保护失败不会反复原样提交，不再把这两类失败混成同一种超时。

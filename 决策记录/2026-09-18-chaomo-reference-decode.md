# 超模图生图提交前没有核验参考图，上传格式声明可能与实际内容不一致

日期：2026-09-18

起因：用户贴出 `PRJ_BHLJ__ABC_EP01_SEG02_TO_SEG03_R01` 的失败日志并说「还有一个这个问题」。任务 `task-1a0b348810f-f5afc726` 从 running 转 failed，服务商回报「参考图无法解码」，错误码 `image_task_error`。用户随后确认原图「在另一台电脑」。

## 查到的机制与证据边界

这次日志是服务商读取输入参考图失败；之前 `completed` 后不返回是结果下载阶段的问题。`image_task_error` 是通用错误码，不能仅凭它判断为内容审核；本次没有改写提示词是正确的。

原始四张图不在当前工作电脑，无法确认本次究竟是第几张损坏、格式声明错误、下载返回网页，还是服务商解码异常。以下是代码检查和离线复现确认的客户端缺口，不把它们冒充为这一单的已证实根因：

1. `ChaomoProvider` 虽然图生图最终要 multipart 文件，却继承默认 `accepts_url=True`。配置对象存储时，共用的 `make_ref_resolver` 会先上传本地图，再由超模适配器下载回来，多一次公开链接传输，也可能拿到错误网页。
2. `encode_ref` 默认保持原图字节，MIME 依据文件后缀。生成结果保存路径经常是预定的 `.png`，实际字节却未必是 PNG。超模 `_ref_bytes` 又盲信 data URI 的 MIME 或 HTTP `Content-Type`，没有按真实内容核对，导致实际 JPEG/WebP 也可能声明为 PNG 或通用二进制。
3. `_ref_bytes` 不验证图片完整解码，HTTP 200 的 HTML/XML、空字节、截断图片同样变成 `image[]` 上传；Base64 失败时返回空元组，只要另一张成功就继续生成，导致参考图静默缺失和编号错位。
4. 本次服务商原话会被归为 UNKNOWN，可能触发换家；换家收到同一张坏参考图不能解决问题。

问题长期没有被发现，是因为原有 multipart 用例只用八字节 PNG 签名充当图片，仅验证接口名、字段名和异步参数；这种假图片在旧实现中也能提交，测试没有验证内容和格式的一致性。新增回归在旧实现上 23 项失败、1 项通过，复现以上缺口。

## 修复范围

- 超模图片声明不需要把本地图转成公网 URL，解析器直接给原始 data URI，适配器解码后仍以 multipart 文件上传。视频接口继续使用公网 URL；任务中明确填写的图片 URL 仍支持下载。
- 上传前逐张严格解码 Base64、使用 Pillow 检查容器并完整加载像素（多帧逐帧检查），仅接受 PNG/JPEG/WebP。上传文件名和 MIME 跟随真实格式。
- 校验和声明修正不重新编码、不缩图、不覆盖文件，PNG 透明度和原始图片字节保留。未新增超模的大小限制；XMD 的 10MB 规则仍只属于 XMD。
- 每张图记录序号、格式、尺寸、字节数和检查结果。任一参考图无效即在提交生成前明确报第几张，并指向任务明细的参考图顺序；不丢图继续提交。
- 新增 REF_INVALID 诊断，区分图片内容问题和缺图/审核问题，阻止同一份坏参考图自动换家。服务商原话里的「参考图无法解码」也能得到这一指引，但不把所有 `image_task_error` 都归成图片错误。

两套体系、资产图、场景状态图、交接板整板/区域图和旧故事板共用图片 worker，因此都经这一检查。一键流水线和生产页单独运行最终进入相同 worker/provider；没有改动它们的调度规则，也没有改其他服务商的图片上传方式。

## 修完能避免什么

以前要等服务商提交、排队后才收到笼统的失败，甚至少传一张图仍然生成。现在本地可识别的坏图在提交前就说明第几张；仅声明格式错误的有效图会直接按真实格式上传。用户在任务明细按顺序找到对应参考图，换成完整的支持格式图片即可重跑，不需要修改提示词或盲目重试整批。

如果所有参考图均已在本地完整解码通过，而服务商仍报同样错误，日志会保留每张图的核验结果及服务商任务号，供核查服务商解析兼容性。此修复无法凭空还原已截断的原图，也不能保证服务商接受本地能读取的所有图片变体。

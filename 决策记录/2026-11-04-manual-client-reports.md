# 通用客户端错误日志主动上报

日期：2026-11-04

## 用户要求与范围

用户要求客户端可以向服务端上报日志，方便定位不同机器表现不一致的问题；随后明确“主动上报”“通用的错误上报功能，切勿 GT 专用”。本轮按用户点击按钮主动提交实现，不增加自动详细报告发送，不限定服务商，不更改 GT 或其他适配器的生成策略。

## 问题机制

原有 `core/cloud_diagnostics.py` / 服务端“请求诊断”只提供基础结果与整条任务耗时。任务细节未被关联到实际使用的模型、Key、适配器或提交/查询阶段；而被公共请求层包装的 401 可能来自 HTTP 状态，也可能来自 HTTP 200 的上游错误正文。缺少可按设备比较的关联证据，只看“失败”不能定位差异。

## 实现

- 在原诊断写入后台队列中增加有限的本机近期记录。请求层使用独立任务上下文，仅保存白名单元数据，不保留正文、完整凭据、提示词或路径。关键结果即使自动基础诊断发送成功也仍保留在近期记录中。
- 公共 HTTP、产物下载、生产失败、本地操作和前端运行时异常均进入同一通用报告。前端记录只发到本机接口；不在打开设置时或错误发生时向远端发送详细报告。
- 客户端“设置 → 错误日志上报”选择问题类型/时段后发送。后台线程采集/提交，显示上报编号与明确接收状态。失败保留报告，手动重试同编号，账号切换后隔离。
- 服务端增加独立接收接口、严格数据模型、请求体限制、登录设备验证、限流、去重和保留上限。后台每个账号增加“客户端日志”，支持设备筛选、详情搜索和 JSON 下载。
- 旧基础诊断协议不增加字段，旧客户端继续兼容。新客户端遇到旧服务器的 404/405 明确提示升级服务端，生产不受影响。

## 为什么这样能帮助排错

以前只有一个任务的汇总错误，现在用户主动提供的报告可以将同一任务的提交、查询和下载对应起来，并对比成功/失败设备的模型、密钥指纹、实际接口状态和适配器摘要。上报故障不会变成生产故障；记录不足和截取数量也会显示，不能把“没有证据”当作“没有问题”。

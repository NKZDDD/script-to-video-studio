# 从已发布的 Studio 2026.10.28.2 恢复独立 C 重抽解锁代码

日期：2026-10-29

用户要求：「在其他机器写的这个解锁哈希锁的代码并没有提交，我希望你通过解包将代码不全，使得代码同步以及查看这个功能修改是否无误」。按上下文“代码不全”理解为补全遗漏代码。

## 为什么本机仍会锁住

线上 R2 和更新服务已发布客户端 2026.10.28.2，但当前分支的 core/client_build.py 仍声明 2026.10.27.2。core/single_handoff.py 的 freeze_source 仍将同 key、同文件名的 C 内容变化视为错误，并在图片生成前抛异常；现有测试也要求这种变化必须被拒绝。其他机器的解锁实现只进入了 EXE，没有进入 Git，因此仅拉取当前分支不能恢复它。

这不是适配包版本差异。Studio-providers-2026.10.28.2.json 是独立服务商适配包；本次恢复的是同版本号的客户端安装包中的生产逻辑。

## 恢复的行为

1. 客户端版本恢复为 2026.10.28.2。
2. freeze_source 增加可选 log 回调，图片生产 worker 传入任务日志。
3. 同 key 的 C 图片内容改变时不再抛异常；改为记录新摘要，并提示旧 A/B、视频可能与当前 C 不一致，需要时重产。
4. 保留内容寻址快照，单次请求上传的仍是计算摘要时的那份 C 图片。旧快照保留，已有 A/B 的来源证据不会被新结果覆盖。
5. 旧来源记录若不是字典会被修复；来源缺失或不唯一仍拒绝，不能把解锁理解为允许错误参考。

两个生产体系共用该图片 worker，改动范围同时覆盖 v34 和 v61。

## 功能审核范围与边界

此次恢复的是已经发布包内的运行实现，不新增自动重产和额外拦截。警告在后续生成 A/B、检测到 C 摘要变化时出现；重抽 C 不会自动重抽所有已完成的 A/B 或视频。若只重抽 C 而复用旧产物，用户仍需自行决定重产范围。

既有材料契约仍强调正式设计换版时的 key/filename 与配对来源。包内没有同步改写这些契约文字。本次保持与发布包一致；运行时的同 key 图片重抽已经允许，不将渲染重抽重新解释为必须重新验收材料。

EXE 不包含未打包的开发测试、原注释和构建脚本，无法声称逐字恢复另一台机器的这些文件。特别是发布说明提到的分体系安装包命名脚本不在包内，本次没有猜测并覆盖本机 tools/build_desktop.py。新增回归测试用于保留已恢复的功能约定。

## 修完能避免什么

从本机继续开发时，不会再因缺失这次提交而把“C 重抽后禁止继续生产”的旧判断带回后续版本。新版 C 会用于后续新任务，来源变更可在日志和证据中追溯；已提交的任务继续取回原结果，避免重复计费或将旧任务错误标记成新 C 生成。

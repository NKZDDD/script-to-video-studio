# Studio 与对外批量版共用认证服务、独立发布更新

日期：2026-10-29。

用户要求：一样要有下载安装更新然后在服务端的页面要可以选不同的应用，但是 key 池子可以通用，对外批量是不是根据我的分配和适配包来看到模型。

## 定性与范围

已有 flavor 将 batch 与 Studio 的 all/v34/v61 发布记录分开，但 client_version_policy 只有一行，全局暂停同时影响两个应用；批量程序此前只有登录门槛，没有下载、校验和安装入口。仅增加 batch 登记无法完成自动更新。

本次改批量版更新器、独立安装器、发布工具，以及认证服务的版本策略/后台页面/统计/命令行。账号、Key 库、授权下发、用量接口继续共用，Studio 客户端无需重打包。旧 Studio 清单无需增加 application 字段也可继续导入。

## 实施

- 服务端按 studio/batch 应用存放校验开关，首次升级复制原暂停状态，之后独立更改。旧接口和命令行未指定应用时默认 studio。
- 后台先选应用，该应用的体系、推荐版本、最低版本、构建记录及统计随之切换；导入其他应用清单会拒绝。服务端也校验 application/flavor 一致性。
- 批量版启动后可在登录前检查更新、下载显示进度、校验大小和 SHA256、重启调用独立安装器。旧版本无法登录时仍可进入更新流程。
- 安装器使用独立安装目录、注册表、快捷方式、互斥体和 R2 路径。安装前等待本应用进程退出；有批次运行时阻止安装，并与新建批次共享同一把锁。
- 当前模型列表仍为账号 Key/模型绑定与批量版已有适配器的交集；未新增运行 Studio 远程 Python 适配包的能力。两种适配器接口不同，不能把 Studio 包当作批量包执行。

## 避免的问题

管理员暂停一个应用不再同时放开另一个；不会把 Studio 清单导入批量发布界面，也不会用 Studio 安装器覆盖批量版。强制更新后用户能在登录前下载正确应用的更新包，不再只能联系管理员手动拿包。Key 调整继续由后台分配，无需重新打包。

## 验证

覆盖独立暂停/恢复、旧策略迁移和重启持久化、错误应用清单、安装包哈希/大小/重定向、运行批次时禁止安装、真实 Windows NSIS 等待进程退出与重启、页面应用切换，以及批量/认证/Studio 全量回归。结果：批量 130 项通过；认证 144 项通过；Studio 3737 项通过、1 项跳过（另有 27 个子测试通过）。EXE 启动与登录前更新入口通过，未发起付费生成。交付 VALIDATION.json 记录文件校验和验收范围。

# 生产页勾选延迟与改写 LLM 排查

日期：2026-10-26

起因：用户反馈“提示词改写 LLM 是不是挂掉了”，以及生产页选中/取消按钮禁用后动作迟迟未显示。

## 定性与范围

- `web/agent.js` 的按钮统一在异步操作结束前禁用；`setSelection` 保存后必须等待整个 `loadProject` 才改变显示。因此几项勾选依赖全项目发布扫描、产物校验、历史任务读取完成。单项、分组、当前结果、全项目全选共用这条路径。
- `server/agent_api.py:project` 为确认单个项目是否登记，每次遍历全部生产目录并读取每个项目的元数据、失败和发布状态；勾选接口还先加载不需要的服务商能力清单。
- `core/agent_projects.py:select` 重复读取任务清单，再通过 `selections` 与自身各写一次勾选文件；原 `selections` 每次读取也写文件。共享盘小文件访问与全局 JSON 锁会放大等待。本地小测试目录、立即完成的接口模拟无法暴露这一时延机制。
- LLM 页面只检查凭据存在，不进行服务商鉴权。当前工作电脑保存的是 `api.paisio.online / gpt-5.6-sol`：模型目录返回 200（107 项，包含该模型），但同一 Key 经 Studio `build_llm` / `LLM.chat` 发起最小连通性调用返回 **401 Invalid token**（约 0.85 秒）。目录可读并不证明 Key 可调用。未回显、改动或提交密钥。此结果仅代表当前电脑配置，不能证明其他电脑配置或服务商整体宕机。

## 修复

- 登记检查保持“配置的生产父目录下直接子目录”边界，只检查本次路径，避免扫描其他项目。
- 勾选接口单独处理，读一次任务、按需写一次勾选文件，返回实际保存的全部任务勾选；查询已有勾选不再重写。
- 页面立即显示勾选和依赖提示，显示“正在保存勾选”；串行保存防止乱序覆盖。返回后更新已确认状态，不再为勾选加载整个项目。
- 保存失败恢复已确认状态，并保留后来尚在排队的操作、明确提示错误。过期刷新和切换项目后的迟到结果不能覆盖新状态。生产计划仍等待勾选成功保存后才读取。
- 不改变认证、生成参数、模型授权或内容审核处理规则。本轮不打包、不上传新版本。

## 验证与交付

- 新增真实浏览器延迟响应测试：保存未返回时立即显示勾选、生产计划等待保存、两次连续保存失败恢复已确认值、旧刷新不覆盖已保存勾选、切换项目隔离迟到结果。相关 UI 测试 **6 通过**。
- 后端专项保证登记检查不遍历项目、保持路径大小写、拒绝未登记/嵌套/非目录路径；勾选保存不加载能力或产物、只读一次任务、只按需写一次、错误输入不改文件。路径大小写细节调整后补验 **3 通过**。
- 全量 `py -m pytest -o addopts= -q`：**3558 passed, 1 skipped，262.97 秒**。日志：`D:/Studio-checks-20261026-selection/full-tests.log`。
- 根因是把简单勾选串在目录遍历、全项目刷新后面，加上没有任何保存中反馈；此前测试只确认最终状态，没有模拟慢共享盘响应。修复后用户立即看到勾选和保存中状态，失败会恢复并提示；不会把未保存操作当作生产计划依据。
- LLM 此次调用没有返回有效正文，实际错误为 `HTTP 401 / Invalid token`。应在“设置 → 提示词改写 LLM”核对实际接口地址及有效 Key；若问题在另一台电脑，不能将本机配置测试替代那台的日志判断。
- 本轮交付源码修复，不改认证策略、适配包和凭据。现有 R2 **2026.10.23.2** 安装包不包含这次修复，需要后续重新打包发布。

# Studio 一键更新方案（待实施）

日期：2026-09-28

状态：仅保存方案，暂不开发、不发布。用户要求：「这个方案保存一下后续再完成」。

## 已确定的方向

用户希望在 Studio 内点击按钮更新，避免每次向其他机器发送安装包、手动替换 EXE。

Studio 固定请求用户自己的服务器接口，查询是否有新版及更新资源地址。客户端不绑定 R2 或某个安装包地址；更新包可以放在 R2、其他对象存储或服务器，迁移资源位置只需修改查询接口返回的数据。

用户原话：「我可以请求我服务器的一个接口查看是否更新和更新的资源地址吗？这样我只需要确保我的查询接口在，我的更新资源可以任意存储位置」。

## 拟议接口（字段尚未最终确认）

固定 HTTPS 查询接口返回最新版本信息，例如：

```json
{
  "version": "2026.09.28.3",
  "build": 2026092803,
  "notes": "本版本更新说明",
  "download_url": "https://downloads.example.com/Studio-20260928.3.zip",
  "sha256": "更新包的SHA256十六进制摘要",
  "size": 165000000
}
```

以上地址、版本和数据仅为示例，不是已部署接口。`build` 拟作为递增版本比较值，`version` 用于显示。还需确定无更新响应、客户端兼容信息、鉴权及错误响应。资源可使用临时签名 URL；链接过期后重新查询，重试时仍需核对版本和摘要。

## 拟议客户端流程

1. 在「设置 → 软件更新」显示当前版本，提供「检查更新」入口。
2. 请求固定接口，比较版本，展示更新说明、下载大小和更新按钮。
3. 点击更新后下载至暂存目录，显示进度，验证安装包及发布信息。
4. 有生产任务时等待任务结束，再由独立更新进程完成程序退出、替换和重启；不直接覆盖正在运行的 EXE。
5. 保留配置、Key、项目、产物和数据目录。检测旧服务商外挂覆盖新版内置适配器的情况，避免更新看似成功却继续执行旧逻辑；具体处理方式实施前确定，不自动删除用户外挂。
6. 保留上一版用于安装失败恢复。失败时给出原因和重试入口。

建议使用发布信息数字签名，客户端内置验证公钥；SHA256 用于文件一致性检查，不能替代发布来源认证。签名算法、签名内容和密钥管理方式后续确定。客户端只负责查询与下载，不封装 R2 上传密钥。

## 发布端流程

构建并验证新版 → 上传完整更新包 → 确认资源可下载 → 更新服务器接口指向新版本。

更新包按版本保留，不覆盖正在提供下载的同一版本文件。查询接口应避免缓存导致客户端长期看不到新版本。日常仍需构建并发布新版，但无需再逐台发送文件。

现有 Studio 尚无这套在线更新机制。首次需分发一次带更新功能的版本，以后才可在程序内更新。当前程序和数据已有分离机制；具体实现需兼容数据目录放在 EXE 旁的旧安装方式。

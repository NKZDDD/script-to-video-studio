# 客户端使用后台 Key 库名称显示服务商

日期：2026-10-22
起因：用户要求「让客户端现实服务端设置的名称就可以」，并询问服务商外挂能否也随后台下发。

## 为什么会有这个问题

服务端 `key_library.configuration` 已下发每条授权的 `key_name`，客户端也保存在账号隔离的内存中，但页面能力声明一直取适配器的类属性 `name`。管理员改的是 Key 库名称，页面读的是另一处固定名称，所以刷新仍看到带原域名的内置名称。此前多 Key 改动验证了模型合并和路由，未把名称接到页面。

## 本次范围与规则

- 复用现有 Key 名称，不增加第二套后台命名字段。客户端共用能力声明在输出时覆盖显示名；服务端不需要新的协议或部署。
- 同一服务商多把启用 Key 按授权顺序合并名称，用 ` / ` 分隔，去重并忽略空名。模型合并与按模型选择 Key 保持现有逻辑。
- 覆盖当前工作台和旧页面的服务商选择、创建入口、并发设置、首选/备用摘要、生产计划、待取回提示，以及外挂扫描/导入报告。两套生产体系及所有任务类型通过同一能力声明取得名称。
- 名称只在展示时替换，不修改服务商 ID、适配器类、调用地址、模型 ID、任务快照或取回凭据。退出登录、切换账号、撤销授权后重新取当前账号名称；无名称时保留内置值。
- 旧页面将名称直接插入 HTML 的三处改为转义，避免后台名称包含引号或标签时破坏选项、标题、配额表。
- 用户本次明确只需名称同步。Base URL 和请求地址没有隐藏；外挂代码自动分发不属于本次改动。已内置或手动导入的适配器可以接收后台 Key/地址/模型，新适配代码仍需安装。

## 修完能避免什么

管理员修改 Key 库名称后，客户端刷新配置即可显示新名，不再需要每次为改名重打包；改名不会把内部 provider ID 当成新服务商，也不会导致旧任务换 Key 取回。多账号之间不会因修改全局适配器名称而串名。后台名称中的特殊字符作为普通文字显示。

## 验证

针对性测试通过 31 项，覆盖两个页面的 bootstrap、服务商扫描、目录失败回退、名称刷新、账号隔离、旧任务快照、双 Key 模型路由，以及实际 JavaScript 下拉渲染的转义和内部 ID 保留。

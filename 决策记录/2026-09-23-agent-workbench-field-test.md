# Agent 工作台实测反馈的 7 个问题

日期：2026-09-23
起因：「我真实测试了一下新版的程序会有以下一些问题，1、创建项目读取的文件没有包含jsonl文件而且按钮ui不对 2、codex不一定在本机运行所以也需要有给其他机器使用然后反向让程序读取的兼容  3、设置中服务商的下拉框样式不太好，4、导入新服务商只能放到文件夹不能通过页面取选择文件导入5、生产中选择东西右边展示左边要用选中的highlight 6、点击查看生产计划后下滑会一致悬浮页面很不协调 7、在制作视频时会提示30秒不在当前模型能力456789 10 11  12 中是什么意思」

## 我查到的

用源码加 313 项的测试项目启动工作台，逐条在页面上看过（`outputs/agent-issue-review/20260923-224717/`）。

1. **读取原文文件**：`web/agent.js` 向导第 1 步的文件控件写死了 `accept=".txt,.md,.docx,.pdf"`，后端 `core/docparse.py` 也只认这几种。
   控件是浏览器原生的 `<input type=file>`，被通用输入框样式套了一层边框，显示英文的「Choose File / No file chosen」，看起来不像按钮。
   生产页右侧的「手动放图」用的也是同一种控件，同一个问题有两处。
2. **Codex 不在本机**：当前设计（`docs/design/codex-production-v7/架构方案.md` 第 183 行）明确要求 Agent 和 Studio 在同一台主机上。
   模板里写的是本机绝对路径，Agent 直接写进 `03_提示词/releases/rNNNN/` 和 `READY.json`，Studio 定时扫描。
   Codex 在另一台机器上时，它既读不到项目，也写不进来。这是新需求，不是 bug。
3. **服务商下拉框**：「服务商」标签和下拉框挤在同一行，下拉框没有和下面的输入框对齐，也没有间距。
   20 个选项的名字里带着域名和括号说明，最长的一个有 40 个字。
4. **导入服务商**：设置里只有「重新扫描服务商」，只能先手动把 `.py` 放进数据目录的 `providers`。页面上没有上传入口。
5. **左侧没有选中高亮**：点左侧资源时只刷新右侧详情（`actions.detail` 只调了 `renderDetail`），左侧树不会重画，所以选中标记加不上去。
   另外，代码给的标记是 `class="active"`，样式表里高亮的规则写的却是 `[data-active=true]`，两边对不上。即使树重画了，也不会亮。
6. **生产计划跟着悬浮**：9 月 20 日按要求把「开始生产」和「生产计划」合成一张吸顶卡片（`2026-09-20-header-production-dock.md`）。
   点「查看生产计划」后，计划详情展开在这张卡片里。往下滑的时候，整块计划（约 230px）一直盖在列表上面。
7. **「30 秒不在当前模型能力 [4…12] 中」**：生产计划校验时长（`core/agent_runtime.py` 第 155 行）。这一段任务要求 30 秒，而当前选的视频模型声明只支持 4–12 秒。
   程序宁可拦下来，也不偷偷截短。4–12 这组数不是程序内置的，只可能来自两处：设置里手填的「已实测的模型时长档位」，或者「刷新模型」时从服务商实时拉回来的声明。
   报错里既没写是哪个服务商、哪个模型、数据从哪来，也没写该怎么办，所以看不懂。

## 直接修的（只有一种合理修法）

- 1 的控件部分：所有文件控件（原文、手动放图、以及第 4 条新增的）改成统一的中文按钮，旁边显示已选的文件名。
- 3：服务商选择改成和其他字段一样的「标签在上、整行下拉」布局。
- 4：设置里加「导入服务商文件」。选中 `.py` 后保存进数据目录的 `providers`，自动重新扫描，并报出这个文件的加载错误和警告。同名文件先备份再覆盖。
- 5：点左侧资源时同步高亮左侧那一行，修正样式规则。
- 7：报错改成写清服务商名、模型、这组时长来自哪里，以及三种处理办法：换支持这个时长的模型；让 Agent 按上限重新切段；服务商实际支持的话，在设置里补上「已实测的模型时长档位」。

## 要你定的

### 1. 创建项目时要读的 jsonl 是哪一种

- **A**：Codex 按旧版材料契约交付的「生产材料.jsonl」（每行一条任务，带提示词、参考图、输出路径）。选中后直接导入成这个项目的任务，不再等 Agent 发布。
  好处：别的机器上做好的材料一步进来；代价：这种项目走旧版材料路线，不是 Agent 发布版本。
- **B**：只是原文存成了 jsonl（比如每行一段剧本）。读成纯文本放进「原文」框，和 txt 一样处理。
  好处：改动最小；代价：jsonl 里的结构信息全部丢掉。

我倾向先确认，因为 A 和 B 是两个完全不同的功能。如果是 A，它其实和第 2 条是同一件事的一部分。

### 2. Codex 在另一台机器上时，材料怎么来回

- **A（推荐）**：交接包。Studio 导出一个 zip，里面有用相对路径写的 Agent 模板、契约、结构定义、完整技能快照和原文。
  Codex 在任何机器上解压，按包里的相对路径产出发布目录和 `READY.json`，再打包带回。Studio 点「导入 Agent 发布包」，按 `READY.json` 里的 SHA-256 校验后，放进 `releases/`，走现有的接收流程。
  好处：任何机器、离线都能用，不用配网络；Studio 这边的校验和本机模式完全一样。代价：每一轮要手动搬一次 zip。
- **B**：共享文件夹 / 同步盘。模板改成相对路径，项目目录放在两台机器都能访问的位置，Studio 照常扫描。
  好处：自动；代价：依赖共享盘，有同步延迟和写一半就被读到的风险，两台机器的盘符也不一样。
- **C**：局域网上传接口。Studio 开一个带口令的接口，远端 Codex 直接把发布包推过来。
  好处：全自动；代价：要开放端口、做鉴权，Codex 所在机器要能连到 Studio，安全面最大。

我倾向 A：它不改变现有的接收和校验，只是在两头各加一道打包 / 解包。

**附带要定的一点**：远端 Codex 做定向修订时，需要看已经生成的图吗？需要的话，交接包要带上图片，体积会大很多；不需要的话，只带文字材料。

### 3. 生产计划的悬浮怎么收

- **A（推荐）**：只有那一行按钮（待生产数量、查看生产计划、开始生产）继续悬浮；计划详情放回页面正文里，不跟着滑。
  好处：保留 9 月 20 日「随时点得到开始生产」的要求，列表不再被挡；代价：滑下去以后要看计划详情，得回到上面。
- **B**：整张卡片都不再悬浮，回到普通布局。
  好处：最简单；代价：浏览长列表时，要回到页首才能点开始生产，也就是 9 月 20 日要解决的那个问题会回来。
- **C**：卡片继续悬浮，但往下滑时计划详情自动收成一行摘要，点一下再展开。
  好处：两头都顾到；代价：交互最复杂。

我倾向 A。

## 已修的部分（1 的按钮、3、4、5、7）

- 统一文件按钮 `fileButton`：原文文件和手动放图都换成中文的「选择文件… / 选择图片…」按钮，旁边显示已选文件名。原生控件隐藏，但键盘仍然能聚焦。

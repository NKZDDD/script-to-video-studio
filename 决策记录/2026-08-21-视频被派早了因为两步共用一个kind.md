# 视频任务被派早 4 分钟：场景状态图和故事板共用一个 kind 名

日期：2026-08-21

按照修改流程规范来再次修改他」
排错包：`排错资料_女频竖屏外婆的旧食谱电影级17环节05_0820_1832.zip`

故事板**一张都没少，全部 ok**（25 条 storyboard 全成功）。
是视频被派早了。

### 机制

`_worker_kind()`（`core/pipeline_v34.py:110`）：

```python
return {"p1": "asset", "p2": "storyboard", "p3": "storyboard", "p4": "video"}[stage_id]
```

`p2`（场景状态图）和 `p3`（故事板）**返回同一个字符串**。
这对选 worker 是对的 —— 注释写着「scstate 和故事板都是出图，走同一个 worker」，
没错。

但 relay 的三个调用全都拿 `s["produce"]` 当 kind：

```python
relay.declare(_s["produce"], ...)      # 谁产出什么
relay.finished(s["produce"])           # 这一类活跑完了
relay.ready_of(s["produce"])           # 就绪判断
```

而 `finished` 在 `core/relay.py` 里的注释写得很清楚：
**「这个信号是等待的终点。」**

于是 **p2 跑完的那一刻就调了 `finished("storyboard")`**，
而故事板（p3）还在跑。从那一秒起，`ready()` 里这一句：

```python
waiting = [f for f in miss
           if self._makers.get(f) and self._makers[f] not in self._done_kinds]
```

对每一张还没出的 sheet 都算出 `waiting = []` ——
判成「没人会做它了」，于是**照旧派出去**（那是刻意设计：让出图那层的硬停
报清缺哪张）。视频撞空，报 REF_MISSING。

`p1`/`p4` 各自独一份，所以只有「视频等故事板」这一条被提前放行。

### 为什么这能存在

一个字符串被用在**两个不同的用途**上，而两个用途对「相同」的定义不一样：

```
选 worker    p2 和 p3 是同一类   （都是出图，走 make_image_worker）→ 该相同
等待终点     p2 和 p3 是两批活   （p2 完了不代表 p3 完了）        → 不该相同
```

这一类错不会报：`finished` 提前触发之后，下游走的是一条**看着很正常的
合法分支**（「没人会做它了 → 派出去让硬停说话」），而那条分支本来是对的。

## 怎么修的

### 一、relay 的 kind 按**步**分，不按 worker 类型分

`_worker_kind()` 保持原样（p2/p3 都是出图、走同一个 worker，那是对的），
新增 `_batch_kind()` 返回步的 id（p1/p2/p3/p4），relay 的 declare / finished /
ready_of 三处全换成它。V6.1 那三类今天不重名、没踩到，但隐患一样，一起改掉。

### 二、缺实际条件就不派（你否掉的那个设计）

`relay.ready_of` 原来是两态，「没人会做它了」返回 True —— **照旧派出去**，
让出图那一层的硬停说话。你的原话：「他缺少实际条件他不能去做才对」。对。
派出去撞一次空，面板上留下的是一条**失败**，而它不是失败，是条件不具备；
两者在面板上长得一样，人就分不出「这条要修」和「这条在等前面」。

改成三态：

```
True   可以跑
False  在等上游那一批，等就对了
None   条件不具备 —— 不发请求，标成没做成并写清缺什么
```

`run_batch` 认第三态，标 TASK_FATAL（重试一个条件不具备的任务只会重复撞空）
并写「条件不具备，**没发请求**：缺 …。而且没有任何一步会做出它们」。

### 三、十一和十二的权威关系（你定的方向）

两个方向各管一头，都做成**结构性**的 —— 昨天证明散文指引拦不住：
同一次运行里 SEG04 遵守了（自己写「SCST_..._SC03_02为LOGICAL_ONLY，无PNG」
且 `reference_order: []`），SEG05 照样引了。

**十一有十二的** —— 新增 `check_scstate_coverage()`：第十一环节跑完立刻查
「每个 SEG 至少有一张会出图的场景状态」。因为 V6.2 要求每个 SEG 都有故事板，
而故事板结构上需要一个主参考。全判成不出图 = 造出一个**做不出故事板的段落**，
而这件事在第十一环节就能查（段落表 + 判定），不用等到第十二环节引了一条、
再到出图前才发现 —— 中间隔着四个环节的钱。

**十二听十一** —— 新增 `split_scstates()`：发给第十二环节的场景状态表分成两组，
`scstates`（会出图的，只有它们能进 reference_order）和
`scstates_logical_only`（只有文字合同的，明说「没有 png，永远不会有」）。
以前两类混在同一个数组里、只差一个 `decision` 字段 —— 模型得自己记住那条规则，
而它记不住。分开发之后这条规则不再依赖模型的记性：它看到的是两个清单，
其中一个的名字就叫「不许当参考图」。

### 四、尺寸按各家 api 规范转换

新增 `core/sizes.py`，按你说的做。各家写法根本不是一套：

```
派欧 / 灵感鸭 / 小裴 / 章鱼   1024x1536      像素
零视                          还多一档 2048x2048
超模 / M86 / 小巴龙            16:9           比例
坤鸡                          1K / 2K / 4K   档位，也收像素
```

挑选顺序，每一步都比下一步保守：清单里有一模一样的 → 用它；有同形状的
（`1024x1536` ↔ `2:3`）→ 换写法不换形状；只有形状最接近的 → 换，**并且出声**；
换不过来 → **停下来让人改配置**，不猜。

两处不猜是关键：
- **档位遇上只收比例的家**：`2K` 说的是分辨率、比例说的是形状，表达的不是
  一回事。按形状硬匹配会算成 1:1（代表像素 2048x2048），或者在只有比例的
  清单里挑出 21:9（「面积」最大）—— 两个都不是任何人的意思。
- **看不懂的写法**：原样发过去的话多数家自己挑一个默认值，图出来了、
  尺寸不是你要的、任务标 ok。

出图和出片都过这一层（`produce._fit_size`）。

## 为什么会有这个问题

一个字符串被用在**两个不同的用途**上，而两个用途对「相同」的定义不一样：

```
选 worker    p2 和 p3 是同一类   （都是出图，走 make_image_worker）→ 该相同
等待终点     p2 和 p3 是两批活   （p2 完了不代表 p3 完了）        → 不该相同
```

而 `_worker_kind` 的注释只解释了第一个用途为什么该相同 —— 它是对的，
只是没说「别拿它当第二种用」。后来加 relay 的时候手边正好有这个字段，
就用了。

这一类错不会报：`finished` 提前触发之后，下游走的是一条**看着很正常的
合法分支**（「没人会做它了 → 派出去让硬停说话」），而那条分支本来是对的。
两个正确的东西接在一起是错的 —— 和 n11/n12 判定打架是同一个形状。

## 修完能避免什么

**视频被派早**：以前视频在故事板还在跑的时候就撞空，面板上留下两条
REF_MISSING「固定故事板不存在」，而那几张图 31 秒到 4 分钟之后就出好了 ——
人看到的是「出片失败」，实际是「排早了」。这个差别看不出来，只能靠
比对时间戳发现（我这次就是这么找到的）。现在故事板那一批没跑完，
视频一条都不会派。

**条件不具备**：以前会派出去撞一次空、留一条「失败」。现在标成
「条件不具备，没发请求」—— 分得出「这条要修」和「这条在等前面」。

**判定打架**：以前要到出图前才发现（第十一环节之后隔了两个环节的钱），
而且靠模板散文约束模型、实测拦不住。现在第十一环节跑完就停，
而且第十二环节根本看不到那几条能当参考图。

**尺寸**：以前请求 `16:9`、超模回一张 `1024x1536` 竖图，任务标 ok，
只有 `ratio_mismatch` 一条提醒躺在日志里（这次 7 张全是这样）。
现在换成这一家吃得下的值，换了形状要出声，换不过来当场停。

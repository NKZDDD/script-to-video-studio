# 服务端统一发布现有服务商适配器

日期：2026-10-22

起因：用户要求“就这样就可以把现有的方法都传到服务端”。前文已经确认：名称与网址分离，服务商和模型由后台配置，接口适配代码也由后台下发；请求继续在客户端直连。

## 定性和范围

原 `studio_login._verify` 仅安装 Key 和 R2 配置；`core.providers` 从内置模块及本机外挂目录发现类。后台改名与代码分发是两个不同机制，所以之前修改 Key 名称并不能更新接口。该行为一直符合原外挂设计，直到改为中央管理才暴露维护成本。

覆盖所有现有 24 个适配器、两套生产体系共同的注册表、登录/刷新、模型目录、设置页凭据解析、两处 UI、后台 Key 库、服务端部署包及桌面安装器。无需新增意图问题：用户已明确批准所有现有适配方法迁移。

## 实施

- 纯数据 JSON 代码包与通用协议校验；服务端不执行 Python，按账号下发入口与依赖，下载复查会话、设备、版本和当前 Key 授权。
- 后台分为当前发布、导入版本、版本历史；导入不发布，历史版本可重新发布回退。
- 客户端从认证响应取得内容哈希，按账号校验/缓存/加载，在切换成功前保留现有注册表；加载错误明确阻止新任务。
- 内容哈希独立模块空间，旧实例保留旧代码；登录退出清除活动注册表。新安装版不冻结 24 个服务商实现，也不附带模型快照。
- Key 名称、地址和模型绑定沿用原逻辑；没有媒体代理、付费生成和线上更新策略操作。

## 修完能避免什么

以后维护现有协议的端点、参数、模型或返回处理，可以导出完整包后在后台发布，各账号刷新后同步；不再靠每台电脑手动复制 `.py`。缺少适配器、版本不兼容或校验失败会直接提示，不会悄悄走 EXE 中过时的实现。新运行库和框架变化仍需升级客户端，客户端代码缓存不等于不可提取。

## 验证

- Studio 全量：3475 项通过；认证服务全量：121 项通过。
- 后台及客户端浏览器验收：导入不发布、发布切换、历史回退入口、窄屏布局、名称转义、退出清空弹窗、空授权账号仍可刷新配置。
- 冻结 EXE：24 项运行库检查通过；通用运行时内置服务商数量为 0，加载完整外部包 24 个适配器均通过能力检查。
- 归档核对：只含 `core.providers` 与 `core.providers.base`，不含 24 个实现模块和旧模型快照；代码包扫描未包含本地配置凭据。
- 保留旧坤鸡 `.py` 外挂与内置源码的一致性，通用页面解析单独使用共用工具，避免老 EXE 外挂依赖新增模块。

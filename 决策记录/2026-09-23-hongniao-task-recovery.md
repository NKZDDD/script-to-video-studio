# 按红鸟任务号批量取回未落盘的视频

日期：2026-09-23
起因：「我现在有一批这种task的任务没有取回，是否有日志，我可以有补丁批量把任务捞回吗」（附截图：EP01-SEG002~006 红鸟任务「查询超过 2400 秒」+「服务商已返回结果，但取回或文件检查失败」）

## 我查到的

**机制**：`core/providers/hongniao.py` 提交成功拿到 task_id 后轮询 `GET /v1/videos/{id}`，
轮询期间的 ConnectionError 只记一条日志、继续查同一个任务；到 `poll_timeout`（默认 2400 秒）
仍未 completed，就抛 `TASK_FATAL + result_download_failed`。诊断码映射成 `RESULT_DOWNLOAD`，
界面上显示为「服务商已返回结果，但取回或文件检查失败（这条不再重试）」——对「超时」这一类，这个标题并不准确。
任务在红鸟那边多半还在跑或已经跑完，但 Studio 没有任何「按已有 task_id 再去取」的入口。

**日志在哪**：
- 生产页那段滚动日志只在内存里（`Job.logs`，最多 500 行），关掉程序就没了。
- 落盘的是每个项目的 `07_检查与记录/failures.json`：`stage="video"`、`target=段落 key`，
  `raw` 字段就是原始报错，含 `红鸟任务 task_xxx`。这是取回用的唯一可靠依据。
- 目标文件路径在 `03_提示词/tasks.json` 的 `video_tasks[].output`，按 `key` 对得上。
- 限制：`failures.json` 按 stage+target 只留最新一条。同一段如果重跑过，旧的 task_id 已经被覆盖。

**一个马上要注意的风险**：出片时判断「做过没有」只看输出文件在不在（`probe.have_output`）。
这几段现在没有文件，**在取回之前点「开始/继续」或单跑这几段，会重新提交、再付一次钱**。

**取回的做法（不管哪种形态都一样）**：扫描 failures.json，提取红鸟 task_id，按 key 找到输出路径；
用 config.json 里的红鸟 Key 查询状态。completed 就用现有的 `save_item` 下载到原路径（带完整性校验、原子落盘），
然后补写视频台账、清掉这条失败记录；still processing 或 failed 只报告、不动。默认只预览，确认后再下载。

## 要你定的

### 1. 工具在哪台机器、以什么形式跑

- **A（推荐）**：放在 `tools/` 下的独立脚本，在装了源码的这台机器上用 `py tools\红鸟任务取回.py <项目目录>` 跑。
  好处：今天就能用，不用重新打包；代价：需要能访问那几个项目目录，且机器上有 Python 环境。
- **B**：做成 Studio 页面上的「按任务号取回」按钮（生产页的失败卡片上）。
  好处：用 EXE 的机器也能用，以后别的服务商也能接；代价：要改 server 和前端，还要重新打 EXE，今天用不上。

### 2. 范围

- **A（推荐）**：只做红鸟。
- **B**：凡是报错里带 task_id 的服务商都做（巨轮、超模等），每一家的查询协议都要单独适配。

## 你的回答

1. 项目在另一台只装了 EXE 的机器上，需要能在那边跑的东西。
2. 只做红鸟。

## 怎么修的

那台机器没有 Python，所以不做独立脚本，把「续查」做进红鸟外挂 `core/providers/hongniao.py` 本身（同一个文件也是内置实现）：

- 提交前先调用 `pending_task(dest)`：从输出路径往上找项目根目录，用 `tasks.json`（以及 Agent 项目的 active-plan）把 dest 反查成段落 key，再到 `failures.json` 里找这一段的 `raw`。
  如果 raw 是「查询超过 / 查询已取消 / 查询中断 / 已完成… / 返回未知状态」这几种，就取出任务号，**只查询不提交**，完成后用原来的 `save_item` 落到原路径。成功后由执行器照常写台账、清失败记录。
- **失败之后提示词改过就不续查。** 改提示词（`prompt_edits._revise_outputs`）和 Agent 发新版本都会换一个新的输出文件名，但段落 key 不变。
  只按 key 反查的话，会把旧提示词生成的成片下载到新版本的位置上：不报错，内容是错的。
  所以要额外比较这一段当前提示词文件的修改时间和失败记录的 `at`：提示词更新就不续查，日志里写明原因，然后按现在的提示词重新提交；提示词文件读不到时也按「改过」处理。
- 「红鸟任务 X 失败：」不在匹配范围内：服务商明确说失败了，重跑就应该重新提交。
- 查询中断时报错原文一律带上任务号，包括用户取消、非临时性错误（比如余额不足）。以前这两种会丢任务号，下次重跑就是重复付费。
  查询返回 404（服务商查不到这个任务）时，报错里故意不写成可匹配的格式，下次重跑就会重新提交，不会卡死在一个不存在的任务上。

## 顺带更正：日志在哪

Agent 工作台版每批生产结束时都会写 `07_检查与记录/jobs/<批次号>/result.json`，里面有每一段的 `diag.raw`（带红鸟任务号）和最后 120 行日志。
每批一个文件，不会被重跑覆盖。所以某一段在 failures.json 里的记录被覆盖之后，还能在这里按任务号找到，再去红鸟后台下载。
只有旧版的生产页，日志才只存在内存里。

## 为什么会有这个问题

出片判断「做过没有」唯一的依据是输出文件在不在。而红鸟这类服务商，提交和取回之间隔着最长 2400 秒的轮询。
这段时间里断网、超时、取消，任务在服务商那边照样会跑完、照样扣费，但我们这边没有文件。
任务号只写在一句报错原文里，没有任何代码回头读它，所以唯一的补救办法是重新提交。
2400 秒对 30 秒长的视频来说不算宽裕，再赶上高峰期排队，一批里挂掉好几条是可以预见的。

## 修完能避免什么

以前：这批段落重跑，会各自重新提交一次，同样的片子付两次钱；原来的任务在红鸟后台跑完也没人去取。
现在：重跑时日志会显示「继续查询这个任务，不重新提交」，跑完的直接下载到原位置。
红鸟那边还没跑完的，就再等一轮；真正失败的，才会重新提交。

# 打包一次要十几分钟，时间花在哪、要不要动

日期：2026-08-27
起因：用户原话「我想知道我现在 script-to-video-studio 打包一次为什么要十几分钟」

## 我查到的

### 时间的实测分解

按 `build/Respect短剧制作平台/` 里各阶段产物的落盘时间（今天 17:23 那次单文件打包）：

| 阶段 | 起止 | 耗时 |
|---|---|---|
| PyInstaller Analysis（走模块依赖图） | 17:23:14 → 17:28:35 | **5 分 21 秒** |
| PYZ（压 47MB 字节码） | → 17:28:51 | 16 秒 |
| PKG（把 409MB 载荷压成 188MB） | → 17:30:37 | **1 分 45 秒** |
| EXE（拼引导程序） | → 17:30:42 | 5 秒 |
| 小计 PyInstaller | | **7 分 28 秒** |
| 自检：把 exe 跑起来 3 次 | 实测单次 `caption --version` = **1 分 3 秒** | **约 3 分钟** |
| 合计 | | **约 11 分钟** |

自检那 3 次分别是：起服务问 `/api/providers/status`、`caption style --help`、`caption --version`
（`打包exe.py` 的 `selfcheck()`）。单文件 exe 每次启动都要把 409MB 载荷解压到 `%TEMP%\_MEI*`，
所以是 3 次 × 1 分钟，不是 1 次。`selfcheck` 里那句「90 秒还没起来…但不该这么久」
就是这个 —— 90 秒的墙已经快撞上了。

### 机制：包里 8790 个 Python 模块，其中约 4800 个跟我们无关

`PYZ-00.toc` 按顶层包数：

```
1902 modelscope     1524 openai      1043 yt_dlp      894 django
 281 pandas          207 fontTools    192 sqlalchemy  176 openpyxl
 138 videocaptioner   ← 真正要的那个
```

链条是这样接上的：

1. `打包exe.py` 里 `cmd += ["--collect-submodules", "videocaptioner"]` —— **全量**收，
   包括 `videocaptioner/ui/thread/`（那是它 PyQt 桌面版的后台线程，我们是网页界面，一行都不走）
2. `videocaptioner/ui/thread/modelscope_download_thread.py:6-7` `import modelscope`，
   `video_download_thread.py:6` `import yt_dlp`
3. modelscope 顺手把 pandas / pyarrow / sqlalchemy / django / psycopg2 / redis / openpyxl 全带进来
   （`modelscope/hub/api.py:270` 等处）

`EXCLUDE` 里排掉了 PyQt5 / qfluentwidgets —— 那挡住了 Qt 的二进制，
**但没挡住这些 ui 模块本身，于是它们的非 Qt 依赖照样全进包**。
排了一半，而少排的那一半正好是更大的一半。

载荷里最大的几个，除 ffmpeg 是真要的，其余基本都是这条链的产物：

```
87.6 MB  imageio_ffmpeg 的 ffmpeg.exe   ← 真要
26.3 MB  pymupdf/mupdfcpp64.dll         ← PDF 兜底，我们自己选的
22.0 + 14.7 + 9.4 + 6.9 + 2.8 MB  pyarrow/*.dll   ← modelscope 带的，一处都用不到
 5.3 MB  psycopg2（PostgreSQL 驱动）    ← 同上
```

核对过：`videocaptioner/core/` 和 `videocaptioner/cli/` 里 **零处** 引用 modelscope 或 yt_dlp。
而且 torch / faster-whisper / ctranslate2 这台机器根本没装，本地转写那条路本来就不通
（`core/subtitle.py:76` 默认 `asr = "bijian"`，在线免费引擎，不下模型）。

### 范围

- 三个 `.spec` 文件（`Respect短剧制作平台.spec`、`-电影级十七章`、`-通用十二环节`、`script-to-video-studio.spec`）
  里同样写着 `collect_submodules('videocaptioner')` + 只排 Qt。改的话它们要一起改，
  否则「用 spec 打的那次」还是慢。
- `--system v34` / `--system v61` 分体系是**接连打两次**，所以那种打法是 ×2 ≈ 22 分钟。

### 追问：Analysis 能不能靠缓存跳过？（查过，不能）

先纠一个说法：Analysis **不是"安装包"**，它不 pip、不联网、不碰 requirements。
它是从 `run.py` 出发，把能 import 到的每个 `.py` 都读进来解析 import 语句、把依赖图走完
（本机 PyInstaller 6.19.0）。8790 个模块走 321 秒 ≈ 每秒 27 个。
所以它的耗时只跟**模块数量**成正比，跟网络和装没装东西无关。

缓存有两层，两层都救不了：

**第一层：`build/*.toc` 的增量复用** —— 这是唯一可能跳过 Analysis 的机制，但失效条件太松：
`PyInstaller/building/build_main.py:604` 把 `pure`（所有收进来的 Python 模块）登记为
`_check_guts_toc_mtime`，而那个函数（`building/utils.py:57-67`）的判据是
**"old TOC 里任何一个源文件的 mtime 比上次构建新，就整个重建"**。

后果：

- 改了 `core/*.py` 里任何一个文件 → 我们自己的代码就在 `pure` 里 → 全量重走 5 分钟
- **连改一行 `web/index.html` 也一样** —— `datas` 也是 `_check_guts_toc_mtime`（同文件 608 行），
  6999 个 DATA 条目里任何一个动过就重建
- 改 `EXCLUDE` / `HIDDEN`（`excludes`、`hiddenimports` 是 `_check_guts_eq`）→ 也失效一次

也就是说这层缓存只在「打完包，一个字没改，再打一次」时命中 —— 而那不是真实场景。
`打包exe.py` 里的 `shutil.rmtree(build)` 让它永远命中不了，但**就算把那行删掉，也基本省不到**。

**第二层：PyInstaller 自己的 bincache（`--clean` 删的就是它）** —— 在这台机器上**根本没启用**。
`building/utils.py:130`：`if not use_strip and not use_upx and not is_darwin: return src_name`。
本机没装 UPX（`which upx` 空）、`strip=False`、不是 macOS，三条全不满足，
所以那个缓存一次都没被写过（`%APPDATA%\pyinstaller` 目录现在是不存在的）。
**结论：`--clean` 在这里是无害的，不是慢的原因，改它不会有任何收益。**

所以能真正砍掉 Analysis 时间的只有一条：**把 8790 个模块降下来**。
那是无条件生效的 —— 不管改了什么、有没有缓存，每次都省。这就是上面第 2 个问题。

## 要你定的

### 1. 单文件（onefile）还是文件夹（onedir）？

这一条单独就值 4 分钟，而且是产品决策，我不能替你定。

- **A（推荐）**：打包默认 `--onedir`，要发单文件时显式加 `--onefile`。
  好处：PKG 压缩那 1 分 45 秒基本归零，自检 3 次启动从 3 分钟降到几秒；
  拿到包的人**双击启动也从 1 分钟变成 2 秒**（现在每次开程序都要等一分钟解压）。
  代价：给别人的是一个文件夹，不是一个 exe，拷贝时不能只拷一个文件。
- **B**：保持单文件。好处：拿了就走，一个文件。代价：打包慢 4 分钟、每次启动等 1 分钟、
  被强杀会在 `%TEMP%` 攒 400MB 的 `_MEI*`。
- **C**：日常开发用 onedir，正式发版才 onefile。好处：两头都要。代价：发版前那一次仍是 11 分钟，
  而且「我测的包」和「我发的包」不是同一个产物。

我倾向 A —— 单文件的唯一好处是拷贝方便，但代价是**每个用户每次启动都等一分钟**，
这个代价是长期的，而拷贝只发生一次。

### 2. 要不要把 videocaptioner 的桌面 GUI 那条链排掉？

- **A（推荐）**：加 `--exclude-module videocaptioner.ui`、`modelscope`、`yt_dlp`。
  好处：模块数从 8790 掉到约 3500，Analysis 那 5 分 21 秒估计降到 2 分半上下，
  包从 188MB 掉到 130MB 左右（估算，要实测）。
  代价：以后如果要用 videocaptioner 的「从链接下视频」或「自动下本地 whisper 模型」，
  得把这几行改回来 —— 但这两个功能只在它的 PyQt 界面里有入口，CLI 里没有，
  我们也没打算走本地转写。
- **B**：只排 modelscope 和 yt_dlp，留着 `videocaptioner.ui`。
  代价：**不推荐** —— ui 模块留在包里但 import 必然失败，正好是这个项目最贵的那类
  「不报错，只是到那一刻才崩」。
- **C**：不动，先只解决第 1 条。好处：改动面最小。代价：Analysis 那 5 分钟一分不省。

我倾向 A，理由是这条链没有任何一处是我们的功能，而 `EXCLUDE` 现在这半排法本身就是个隐患：
下次 videocaptioner 升级、ui 里多 import 一个重货，包又会无声地长大几十 MB。

### 3. 自检要不要少启动两次？

现在起 3 个进程验 3 件事。可以合成 1 次（服务起来之后加一个接口，让它在同一个进程里
自己跑一遍字幕 CLI 的 `--version` 和样式清单）。

- **A（推荐）**：合成 1 次。好处：省 2 次解压；onedir 之后收益小一点，但仍省十几秒，
  而且日志更清楚。代价：要在 server 里加一个只给自检用的接口，多一处代码。
- **B**：不动。三次启动各自独立，验的东西边界清楚，坏了一眼看出是哪一件。

我倾向 B **如果**第 1 条选了 A —— onedir 之后 3 次启动一共才几秒，这一条就不值得动代码了。
第 1 条要是选 B（保留单文件），那这一条必须选 A。

# 把所有服务商功能整成一个可并发调用的小工具

日期：2026-09-04
起因：用户原话——「把现在项目中包含的服务商所有功能都整成一个可以并发调用的小工具，因为comfyui只能同步太慢了」

## 我查到的

### 机制：慢的不是协议，是入口

ComfyUI 的执行模型一次只推进一个节点。29 个模块 108 个节点（`respect_comfyui/__init__.py`
的注册表）里，每个出图/出视频节点都是**一次一条、原地等轮询**——鹤/坤鸡/超模那些
视频节点单条就要几分钟，图里排 20 条就是老老实实串行等 20 次。节点本身没写错，
是 ComfyUI 不给并发。

### 并发闸门也已经写好，不用重造

- `core/executor.py:9-14` 三层闸：批内线程池 → 每家配额信号量（跨 job 共享）→ 全局总闸
- `core/accounts.py` 按账号排队：HVTALD 那种「一个账号同时只能跑一条」的家，
  并发上限 = 账号数，服务商粒度的闸表达不出来
- `config.json` 里 `limits/global` + `limits/per_provider/*` 已有 15 家的配额

**所以这次要写的是「批量入口」，不是「18 家协议」。** 真正的风险在于选错落点，
把同一批协议养出第三份——插件节点和 providers 已经是两份了。

### 范围：这句话能覆盖到哪

1. 出图 `generate_image`、2. 出视频 `generate_video`（18 家，已覆盖）

4. 素材上传换公网 URL（upload_nodes；studio 侧 `core/uploader.py`）——
   注意这条**不是可选项**：鹤 SD2、一手、智这些 `ref_mode="url"` 的家，
   没有它带参考图的任务根本发不出去（或者更糟：参考图被静默丢掉，图照出、人不对）

## 要你定的

### 1. 这个小工具长什么样，怎么调它？

- **A（推荐）命令行批处理**：`batch run tasks.json -j 8`，一份任务清单进去，
  成品目录 + `manifest.json`（每条的 provider/model/耗时/失败原因）出来。
  —— 好处：最小、最快能用；ComfyUI、脚本、Studio、手工都能调；失败可以只重跑失败的那几条。
  代价：ComfyUI 图里那套连线用不上了，得另外准备清单（可以提供一个"从工作流导出清单"的小脚本）。
- **B 常驻本地 HTTP 服务 + 一个薄 ComfyUI 节点「投递到并发池」**：继续在 ComfyUI 里画图，
  节点只提交不等待，池子在外面并发跑，回头再取结果。
  —— 好处：现有工作流的用法基本不变。
  代价：多一个常驻进程要管；**而且并发度仍受 ComfyUI 限制**——一个节点还是一次投一条，
  除非节点改成吃提示词列表，等于 108 个节点各要改一版。
- **C 在 ComfyUI 里做「批量并发节点」**：一个节点吃 N 条提示词，内部开线程池。
  —— 好处：完全不出 ComfyUI。
  代价：跨图并发做不到（ComfyUI 一个 prompt 只跑一条链），而且这是最贵的一条：
  每家都要新增一个批量版节点。

我倾向 **A**。你说的痛点是「comfyui 只能同步」——那就别在 ComfyUI 里解决它。
A 做完之后，B 只是在 A 外面加一层 HTTP，随时能补；反过来不成立。

### 2. 这个工具住在哪个仓、用哪一份协议实现？

（`script-to-video-studio` 是独立 git 仓 `NKZDDD/script-to-video-studio`，嵌在插件仓里）

- **A（推荐）住 studio 仓，直接复用 `core/providers` + `executor.Gate` + `accounts`**，
  作为 `run.py batch` 子命令或 `bin/` 里一个入口。
  —— 好处：18 家协议**一处维护**，改一次两边都对；三层闸和按账号排队白捡；
  凭据直接读 `config.json` 里已经填好的那份。
  代价：ComfyUI 那边要用它，得能找到 studio 目录（插件仓里就有，加一条路径即可）。
- **B 住插件仓，独立写一份轻量实现**，不依赖 studio。
  —— 好处：插件自带，单独发出去也能用。
  代价：**18 家协议养第三份**。现在已经有两份了，而这类重复的表现形式不是报错，
  是某一家改了协议只改了一份——另一份继续静默丢参考图。
- **C 住插件仓，但把 studio 的 providers 目录复制过去**。
  —— 和 B 同病，只是复制的时刻不同。

我倾向 **A**，理由就是上面那条：这个项目最贵的问题类型是「同一个毛病有几处、只改了其中几处」，
主动再造一处是往枪口上撞。

### 3. 「服务商所有功能」这句话，覆盖到哪一层？

- **A（推荐）出图 + 出视频 + 自动上传换 URL**（18 家全覆盖）。
  上传不是加料，是 `ref_mode="url"` 那几家的前提条件，不做的话它们带参考图就跑不了。
- **B：A + LLM 对话并发**（Chat / Responses / Claude；`core/llm.py` 已有实现）。
  —— 并发跑提示词改写、批量审片这类活会快很多；代价是工具从「出片」变成「出片 + 文本」，
  任务清单要多一种类型。
- **C：B + 本机后期**（拼接 / 字幕 / 压制，`video_edit_nodes`、`core/subtitle`）。
  —— 这些是本机 ffmpeg 活、不是服务商的，而且 studio 已经有一整套；
  塞进这个工具会让它不再是"小工具"。

我倾向 **A**，先把最耗时、最该并发的那部分做扎实。B 随时能加一种任务类型补上。

### 4. 并发控制做到什么程度？

- **A（推荐）复用现成的三层闸 + 按账号排队**，读 `config.json` 的 `limits`。
  —— 好处：不会把某一家打爆（打爆的表现是"生成失败"，看不出是自己撞的）；
  HVTALD 这种按账号串行的家能正确并发。代价：几乎没有，代码是现成的。
- **B 只做一个全局 `-j N` 线程池**，简单粗暴。
  —— 好处：更小更好懂。代价：多家混跑时按最保守的家设 N 就浪费，按最宽的设就打爆某家；
  HVTALD 一定会撞车。

我倾向 **A**。这一条如果选 B，第一次跑 50 条混合任务就会踩到，而且报错信息帮不上忙。

### 做的过程中查出来的五个问题

都是「不报错、只是少了或者错了」那一类，逐条修了并补了测试：

1. **`config._merge` 是浅拷贝** —— 磁盘上没有 `providers` 这一节时，
   `load()["providers"]` **就是模块级 `DEFAULTS["providers"]` 那个对象本身**。
   往里写一把密钥等于改了默认值。表现：在页面上删掉某家的 Key、保存、刷新，
   **它又回来了**，看起来像配置文件没保存成功。改成深拷贝。
2. **「这家不做出图」排在「没填密钥」后面** —— 于是永远轮不到它说话。
   阿珂只做视频，选了出图却回一句「还没填密钥」；人跑去填完密钥，
   再撞一次才知道这家根本不做出图。支持什么是类属性、不需要密钥就知道，提到前面。
3. **坏 JSON 被静默吞成「任务清单是空的」** —— `_body()` except 掉返回 `{}`。
   人会回去检查自己那一屏提示词（明明写着），查不到是请求根本没送到。改成响亮失败。
4. **整批致命时把没发出去的也报成「失败」** —— 余额不足停批，20 条里实际只发了
   前 2 条，却报「失败 20」。看到这个数会以为被扣了 20 次，然后去查账单查半天。
   新增「未发」状态，并写明「没扣钱，可以直接重跑」。
5. **「为什么没重试」只进日志、没进 `task.error`** —— 小霸龙那种按次计费不得重试的家，
   manifest 和页面上只显示「网络抖了」。看的人会以为重试设置坏了，
   然后手动重跑整批，**付两次钱**。

### 为什么会有这些问题

前四个的共同机制：**这套代码原来只在一个「有项目目录、有前端、有人盯着」的
环境里跑**。studio 里 `load()` 拿到的配置马上就被整份写回，浅拷贝的别名活不过
一次保存；请求都由自家页面发，不会有坏 JSON；批次由人盯着，"失败 20"当场就能
问一句。搬到一个**独立、无人值守、可命令行调用**的程序里，这几条假设全部不成立
—— 而它们失效时都不报错。

第 5 个是另一类：**判定做了、但只说给日志听**。程序自己知道「这家不能重试」，
也照做了，可这个判断没有写进那条任务的记录里。留下来的证据和实际行为对不上。

### 修完能避免什么

- 不会再有「我删了那家的 Key，它自己回来了」这种查不到源头的现象；
  也不会有一把真密钥留在进程默认值里被后续 `masked()` 一起合出去。
- 选错服务商时**第一句话**就说清楚是选错了家，而不是让人先去填一遍密钥。
- 命令行/脚本调接口发坏了请求，当场说「请求体不是合法 JSON/UTF-8」，
  而不是让人对着一屏写好的提示词怀疑人生。
- 余额不足停批时，账单上扣了几次、页面上就报几次「失败」，
  剩下的明确标「未发（没扣钱，可以直接重跑）」—— 不用再去对账单。
- 小霸龙那种按次计费的家失败时，失败原因里直接写着「只发了一次、
  要重跑请自己确认没扣过钱」，不会有人以为重试坏了而手动重跑整批。

# 生产流程五步：现状对照与缺口

日期：2026-09-24
起因：「我希望的流程是这样的现在的流程我是打算这样 手动codex（稳定之后转自动）—扔到自动化（涉及图片，视频的重试机制和回收保障）—跑出全部视频（视频拼接手动选择，涉及到重新抽卡完成后拼接）—剪辑（看剧本而定）—加字幕」

## 我查到的

| 步骤 | 现在有的 | 缺的 |
|---|---|---|
| 1 手动 Codex | 本机 Agent 契约；昨天加的交接包（跨机器） | 「转自动」是以后的事，这次不做 |
| 2 自动化（重试 / 回收） | 临时错误自动重试（默认 2 次）；上游失败时下游不提交；失败落盘；已有成品不重复生成；红鸟可以续查 | 见下面 2a、2b |
| 3 跑出全部视频 → 抽卡 → 手动选择拼接 | 按集拼接，按任务清单顺序，要求整集每一段都有效 | 见下面 3a、3b |
| 4 剪辑 | 程序里没有，在外部剪辑软件里做 | 这次不做 |
| 5 加字幕 | 工作台里只能处理 `06_成片` 下由 Studio 拼出来的 MP4；独立字幕工具可以处理任意视频 | 外部剪好的片子要放回 `06_成片`，或者用独立字幕工具 |

**2a 回收保障：除红鸟外，没有。而且轮询超时会让同一段重复付费。**
- 大部分服务商走通用轮询 `apiutil.poll`。超时抛出的是 `RETRYABLE`（`core/apiutil.py` 第 1088–1097 行），巨轮、好漫剧、Gate 各自的轮询超时也是 `retryable`。
- 执行器看到 `RETRYABLE` 会把整个任务重跑（`core/executor.py` 第 480–484 行，Agent 模式默认 `max_retry=2`）。重跑就是重新提交。
  所以一段视频在服务商那边排队久了一点，最多会被提交 3 次、付 3 次钱，前两个任务没人去取。
- 提交时网络断开（`RETRYABLE`）也会走同一条路；而服务商那边可能已经建好任务、开始扣费了。
- 任务号只写在报错文字里，程序重启或点「停止」之后，没有任何地方能把在途任务接回来。昨天给红鸟做的续查只覆盖红鸟一家。

**2b 换家：Agent 模式没有。** 旧版有「出图出片优先级」，一家挂了自动换下一家补剩下的。Agent 生产每类只用一家（`agent_runtime.start`），这家不行就停在那里。

**3a 抽卡：没有。** 每段只有一个固定的输出路径，文件存在就直接复用。想重做只有两条路：改提示词（会生成新的输出文件名），或者让 Agent 发新版本。没法「同样的提示词再出一条，挑一条好的」。

**3b 手动选择拼接：没有。** `/api/agent/assemble` 按任务清单顺序把整集拼起来，每段只能用那一个文件，不能换、不能跳过。

## 要你定的

### 1. 抽卡怎么留版本

- **A（推荐）**：每段可以有多个版本。对某一段点「重新抽卡」，用同样的提示词和参考图再出一条；所有版本都保留，并排预览，选一个作为「采用版本」。拼接时每段用它的采用版本。
  好处：能比较着挑，抽坏了也不丢原来的；代价：每抽一次付一次费，要新增版本记录。
- **B**：重新抽卡直接替换，旧的挪进备份目录，每段始终只有一个版本。
  好处：简单；代价：不能并排比较，想换回旧的得手动去备份目录找。

附带：只做视频（推荐，你说的是视频拼接），还是图片（资产图、交接板）也要能抽卡？

### 2. 回收保障做到什么程度

- **A（推荐）**：所有服务商统一。提交成功就把任务号记到这一段的记录里；轮询超时、网络中断、点停止、程序重启之后，重跑这一段时先续查旧任务，不重新提交。只有服务商明确回复失败，或者查不到这个任务，才重新提交。轮询超时不再触发自动重跑。
  好处：不会再为同一段重复付费，也不会丢已经跑完的成片；代价：要逐家核对查询接口（有的家任务结果只保留一段时间），工作量比较大。
- **B**：只止损。轮询超时和提交时网络中断改成「不自动重跑，停下来提示」，不做续查，旧任务需要你去服务商后台自己取。
  好处：改动小，马上不再重复付费；代价：回收还是靠人工。

### 3. 一家服务商挂了要不要自动换家

- **A**：不换（现状）。停在这一家，报出原因等你处理。
  好处：同一集用的是同一个模型，风格一致；代价：要人盯着。
- **B**：按设置里的优先级自动换下一家，补剩下的段。审核拦截、参数不合法这类换家也解决不了的错不换（和旧版规则一样）。
  好处：无人值守时能跑完；代价：同一集里可能混用不同模型，画风不一致，可能还得回头重抽。

### 4. 拼接时手动选择的范围

- **A（推荐）**：拼接前出一张本集清单，按剧本顺序列出每一段，每段选用哪个版本（默认是采用版本），也可以临时去掉某一段；顺序不能改。确认后拼接，原片保留。
  好处：配合抽卡刚好够用；代价：顺序调整、插入外部素材要到剪辑软件里做。
- **B**：在 A 的基础上还能调整顺序、插入外部视频。
  好处：简单的剪辑不用出程序；代价：等于在程序里做一个简易剪辑器，和第 4 步「剪辑」重叠。

**我建议的顺序**：先做 2（回收），因为它现在就在让同一段重复付费；然后做 1 和 4（抽卡和拼接清单）；3 看你的回答。

## 第 2 项：回收保障（已实现）

**做法**：每个输出一份记录 `07_检查与记录/submitted/<输出路径散列>.json`。提交成功拿到任务号就落盘，下载成功就删除。
记录里有任务号、查询方式、服务商、模型、账号显示名和内容指纹，**不写任何密钥**。

- **记任务号**：公共轮询 `HttpSession.poll` 一开始就自动记下任务号、查询路径和结果解析方式，覆盖 13 家。
  自己写轮询的 7 家（巨轮、Gate、好漫剧 Omni、HVTALD、XMD、红鸟、云绘）在拿到任务号时自己调用 `submitted.remember()`。
  只在生产工作函数用 `submitted.tracking()` 声明了「这是哪个输出」时才落盘，别处调用轮询不会留记录。
- **续查**：出图和出片的工作函数调服务商之前先看记录。有记录、而且内容指纹没变（提示词、参考图、尺寸 / 时长 / 比例 / 清晰度、服务商、模型），就调用 `provider.resume()`，只查询不提交。
  - 基类的默认续查按记下的方式重放公共轮询，再像生成时一样 `save_item`（查过这 13 家，查到结果后都是这一步）。
  - 7 家特殊的各自覆盖：用自己的轮询函数；超模出图续查后也做图片信息核验；坤鸡先切回出片用的那把 Key。
  - 按账号排队的服务商（HVTALD）续查时只等提交时那个账号（账号池新增 `slot(prefer=...)`）。那个账号如果已经不在列表里，就说明原因后重新提交。
- **什么时候丢掉任务号**：只有服务商给了结论才丢——回复失败（`task_failed` 和各家自己的失败分支都打上 `task_finished`），或者查询连续 404。之后下次生产重新提交。
  内容指纹变了，会在日志里写明「旧任务的结果不再对应这一段」，然后重新提交。输出文件已经存在（比如手动取回放了进去），跳过时顺手清掉记录。
- **轮询超时**：还是 `RETRYABLE`，执行器照样自动重试，但重试时会读到记录、走续查，等于接着等同一个任务，不会再提交一次。
- **页面上的出路**：生产页左侧树显示「已提交待取回」；右侧详情写明服务商、任务号、提交时间，并提供「放弃这个任务，下次重新提交」（生产进行中不允许放弃，并要二次确认）；生产计划写明「其中 N 项先续查原任务，不重新付费」。
- 红鸟原来从 `failures.json` 找任务号的办法保留着，给旧版 EXE 和已有的失败记录用。XMD 和红鸟对新记录模块做成「有就用、没有就跳过」，保证它们仍然能当外挂装进旧版 EXE。

**验证**：新增 `tests/test_submitted_recovery.py` 11 项：
- 超时后重跑只续查、提交次数保持 1、记录里没有多余字段；
- 服务商回复失败 / 查不到任务时丢掉任务号，下次重新提交；
- 提示词改过就放弃旧任务，并说明原因；
- 输出已存在时清掉旧记录；
- 生产以外调用轮询不留记录；
- 无法重放的解析方式会拒绝，并指出出路；
- 账号池能等到指定账号；
- 巨轮和 Gate 的记录与续查；
- Agent 页面显示待取回，并且可以放弃。

两处按源码断言接线的旧测试（`test_accounts.py`）按新写法更新，意图不变。全量测试通过，浏览器验收 7/7、7/7。

## 第 1 项和第 4 项：重新抽卡、拼接清单（已实现）

新模块 `core/assemble.py`。

- **重新抽卡**（`/api/agent/reroll`，只针对分段视频）：把现在的文件移到 `05_分段视频/_抽卡备份/<原名>_<时间>.mp4`，清掉这一段的提交记录，自动勾选，然后按正常流程「查看生产计划 → 开始生产」。

- **拼接清单**：
  - `/api/agent/assemble-plan` 返回本集分段（按剧本顺序，标出哪些还没有有效视频），以及可以插入的视频（抽卡备份、`06_成片/插入素材/`，新的在前）。

## 补充：提交不确定时不再自动重发

起因：上面查到的最后一处。公共请求函数遇到网络超时或网关错误时，会把 POST 自动重发最多 3 次，「提交」本身也包括在内；回执丢了就会多出任务、多扣费，而且连任务号都拿不到。

问用户的选项：图片和视频都停止自动重发 / 只停视频 / 保持现状。用户选「图片和视频都停止自动重发」，停下来提示去服务商后台核对。

**做法**：
- **什么算提交**：生产一个输出、还没拿到任务号时发出的 POST（`submitted.submitting()`）。同步出图的整个请求也算。拿到任务号之后的 POST（比如 Gate 用 POST 查询）不算。提交前的上传显式传 `submit=False`（小霸龙的 `/v1/assets/uploads`）。
  旧版流程里，审核被拦后会改写提示词重新提交；每次调用服务商生成之前都会重置这个状态（`submitted.new_attempt()`），所以重新提交同样受保护。
- **什么算不确定**：请求已经发出但没收到回复（读超时、连接中途断开、200 但正文不是 JSON），或者网关返回 5xx。报 `submit_uncertain`，属于 `TASK_FATAL`，执行器不会重试；对应新的诊断码 `SUBMIT_UNCERTAIN`，加在目录末尾，并列入「不自动换家」。
  能确定请求根本没到服务商的（连不上、域名解析失败、TLS / 代理握手失败），以及限流 429，照常重试，因为这些情况下服务商肯定没建任务。
- **HVTALD**：它的 actionId 是本地生成的，改成投递前就记下。投递后不确定（断线、5xx、200 空正文），就保留记录，下次按 actionId 去 `outs/` 找成片，不重新投递。
  明确被拒、4xx、根本没发出去这几种情况，则去掉记录。它原有的测试「502 要自动重试」按新规则改写成「502 不重投、改为按 actionId 续查」，另外补上 4xx 的情况。
- 红鸟和 XMD 原本就是「提交不确定不重发」，这次没改。

**验证**：新增 7 项测试，覆盖：
- 读超时、连接中途断开、502 三种情况都只发一次，并报「提交不确定」、不换家；
- 从没连上和 429 照常重试；
- 生产以外、`submit=False`、拿到任务号之后的 POST 都不受影响；
- 改写提示词后重新提交再次受保护。

全量测试 2737 项通过。

**代价（用户选择时已经说明）**：同步出图（提交即生成、要等几分钟的那类）遇到读超时，不会再自动重试。要先到服务商后台核对，确认没有生成再重跑这一段。

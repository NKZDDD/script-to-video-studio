# 通用错误日志主动上报

日期：2026-11-04

客户端新增“设置 → 错误日志上报”。这是所有服务商和客户端操作共用的排错入口，由用户点击发送；不是 GT 专用功能，也不会自动向后台发送详细报告。原有的基础“请求诊断”保持原来的行为。

## 使用

1. 在升级后的客户端复现问题，打开“设置 → 错误日志上报”。
2. 选择问题类型（生产任务、连接/超时、界面操作、其他）和最近 1 小时或 24 小时，点击“上报日志”。
3. 等待显示“服务器已收到日志”，将上报编号发给管理员。编号生成不代表服务器已经收到。
4. 管理员进入“账号管理 → 对应账号 → 客户端日志”，查看该编号。可按设备筛选报告，在详情中搜索服务商、模型、任务 ID 或错误，也可下载脱敏 JSON。
5. 发送失败时点击“重试本次上报”。重试使用原编号和已采集的报告内容，服务端去重；不会重新提交生产任务，也不会自动反复发送。

上报在后台线程进行，不占生产任务名额，不在等待网络时持有登录状态锁。发送期间用户可继续使用客户端。

## 内容与排错范围

- 客户端版本、已验证的构建标识、设备标识、操作系统、当前适配包版本。
- 生产请求的服务商、完整模型名、Key 来源、后台 Key ID、实际请求密钥的指纹、适配器来源/版本/摘要、代理配置模式。
- 提交、查询、下载和任务结束阶段，接口 HTTP 状态、错误内容中的上游 HTTP 状态、服务商/上游请求编号、耗时、已知错误类别及代码位置。
- 成功记录也会保留，便于比较成功机器与失败机器。重复成功轮询只保留首次和状态变化，失败请求保留。
- 本地操作的状态/耗时，生产任务预处理或执行失败，以及前端运行时异常的脚本名、行列号。

HTTP 请求细节覆盖使用 Studio 公共 `HttpSession` 的适配器；自行使用 SDK 或独立网络实现的外挂，仍有任务结束/失败记录，但不保证拥有 HTTP 阶段明细。一条请求记录对应一次公共请求调用，内部重试不逐次展开；请求和下载耗时包含内部重试、响应处理，不是纯网络耗时。跟随系统代理表示配置模式，不证明某次请求实际经过了哪个代理。

不会自动收集或上传完整 Key、密码、Authorization、提示词、请求正文、素材、截图或完整本地路径。代码位置只保留文件名、函数名和行号，Key 指纹用于比较是否同一把密钥。报告中的接口状态与上游状态分开显示：HTTP 200 的正文中出现上游 401，不应直接解释为客户端到网关的鉴权失败。

这是一项诊断功能，不修改模型参数、鉴权规则、重试策略或原任务 ID 的续查策略，不能据此认定某个已有的 401 已经修复。

## 保留范围与兼容性

- 本机最近诊断：最多 2000 条，最多 7 天；每次主动报告取所选时段最近最多 200 条，总请求体不超过 256 KiB。详情显示截取省略、队列丢失及存储异常。
- 本机报告：保留最近 7 天，已完成/失败的历史报告最多保留 20 份；不自动发送。中断的上报可在重新登录原账号后手动重试。
- 服务端报告：最近 30 天，全站最多 500 份。客户端报告按验证后的账号归属，设备标识由服务端散列保存。只有管理员可读取；其他账号不能通过编号访问报告。
- 升级前未采集的详细请求不能补录。没有报告不能证明用户没有操作、没有故障或网络正常。
- 此次源码变更没有打包、上传 R2 或部署线上服务。

## 更新顺序

先更新服务端，再更新客户端 EXE。服务端安装步骤沿用现有服务端升级流程：备份数据库，替换程序及 `studio_auth/web/` 静态资源，保留原 `data/`、环境与配置，然后重启服务。启动时自动创建 `client_reports` 表，不需要手工改数据库，不新增运行依赖。

旧客户端仍可使用原接口。新客户端连接旧服务端时，主动上报会提示需要升级服务端，不影响原来的登录、生产或基础诊断。发布新 EXE/服务端包时需包含本文对应的源码与静态资源；当前没有新的可发布版本号或安装包。

验收时在测试账号点击一次上报，确认客户端显示“服务器已收到”，后台可找到同一编号；模拟断网后手动重试，应仍只有一份报告。

# 服务端 1.6.4：客户端版本统计

后台「客户端版本」新增独立的「版本统计」模块，与概览、测试登记、正式发布、构建记录并列。现有带版本信息的 Studio 无需重打 EXE。

## 能看到什么

- 最近 7、30、90 天或全部记录，支持按体系筛选。
- 上报账号数、仍有旧版设备的账号数、低于强制更新门槛的账号数，以及版本或构建信息待核实的账号数。
- 按版本、体系及构建状态列出人数和设备记录，可进一步查看账号、设备名称、最后上报版本与时间。
- 区分高于推荐版本的已登记测试包、信息不足、构建未登记和构建校验码不符。
- 区分尚未采集、观察期内未再上报，以及停用/到期账号。可按账号搜索，设备明细每页 50 条。

点击统计卡片筛选对应账号；点击版本行「查看账号」查看该版本的设备；「去设置更新」跳转到所选体系的正式发布设置。**统计不会自动提高最低版本或发布更新**，仍需管理员确认后保存。

## 统计口径与限制

采集点是成功的登录、会话校验和续期。版本门槛与账号认证顺序保持原样；未通过校验的请求不计为用户，公开更新检查也不计为账号。客户端提前被强制更新拦截后，后台只保留其之前最后一次成功上报的版本及时间。

同一「账号＋设备＋体系」只保留最近一次上报，重复校验、重新登录不会增加设备数；升级后替换对应版本。多设备账号可以同时出现在多个版本中，因此版本人数和卡片人数不可相加。同一电脑的不同体系分别计为设备记录；旧版未上报体系时单列未知记录，不推断其属于哪个体系。

默认看最近 30 天，以服务端接收时间为准。统计账号须仍启用且未到期；暂停版本校验期间也能采集，最低门槛卡片展示恢复原规则后涉及的账号，不表示暂停期间已被拦截。覆盖数中的全站有效账号、尚未采集和停用/到期数不受体系筛选影响；未再上报数按当前所选体系与观察期计算。

**升级服务端后才开始积累数据，不能从旧会话推断历史版本。** 无版本头的旧客户端可以归为信息不足，但必须先通过当前版本政策与正常账号认证；不会为采集而自动放宽门槛。

版本和构建校验码属于客户端声明，可能被伪造。统计适合发现长期停留旧版、未知构建等线索，不能单独证明破解，也不能发现完全绕过本站的调用。账号密码、登录令牌、服务商 Key、原始设备标识均不会返回到此页面；设备仅显示名称与账号范围内的短标识。

## 部署

先保留数据库备份，再把 ZIP 内 `respect-studio-auth/` **里面的内容**合并覆盖到：

```text
/www/wwwroot/respect-studio-auth/
```

保留现有 `data/`、`.venv/`、`.env`、`deploy/runtime.env`，不要删除整个目录或套一层同名文件夹。本次使用原依赖，启动时自动补建统计表，不改已有账号、Key、推荐版本、最低版本或暂停状态。

宝塔终端只复制以下命令（不含终端提示符）：

```bash
systemctl restart respect-studio-auth
curl --retry 5 --retry-connrefused --retry-delay 1 -fsS http://127.0.0.1:8781/health
```

应显示版本 `1.6.4`。若由宝塔 Python 项目管理进程，则在该入口重启，不重复启动第二个进程。

打开 `https://login.respect.chat/admin/`，Ctrl+F5 刷新，进入「客户端版本 → 版本统计」。让一台已登记版本的 Studio 正常登录或续期后，刷新统计验证。首次显示 0 或尚未采集是正常的，不代表用户已全部升级。

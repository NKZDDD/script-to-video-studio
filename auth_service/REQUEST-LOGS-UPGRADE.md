# 账号请求诊断升级（服务端 1.9.0）

后台入口：`https://login.respect.chat/admin/` → 账号列表 → **请求诊断**。

## 这次解决什么

旧版用量对账只记录生产结果，登录连接错误又统一显示“无法连接”。服务端也看不到未到达它的请求，因此不能据此判断是客户网络、代理、服务端处理还是本地文件操作慢。

新版保留两类证据，按账号、设备、收到时间、类型及成功/失败筛选：

- **服务端收到**：登录、校验、续期、退出、R2 签名及适配器请求的 HTTP 状态和应用处理耗时。失败登录中的账号名标为“未经认证”；有会话凭据的失败请求可归到对应账号，但不代表校验成功。
- **客户端上报**：登录请求总耗时及 DNS、TLS、超时、连接、HTTP 错误分类；LLM 调用、生产任务操作的结果与总耗时；生产页勾选、补全依赖、预览计划操作，以及超过 1 秒或出错的项目读取。

登录请求的两端共用请求编号，可复制到筛选框对照。服务端时间从应用收到请求起计，不包括请求抵达 Nginx 之前的等待。客户端时间也包含传输、代理和解析，**两端耗时的差值不是精确网络延迟**。LLM/生产耗时包含等待、重试及轮询，不是单次 HTTP 耗时；生产任务错误也不等于远端生成已经失败。

## 安装顺序

1. 先备份现有数据库，在宝塔终端只复制代码块内的命令：

```bash
cd /www/wwwroot/respect-studio-auth
runuser -u studioauth -- .venv/bin/python -m studio_auth.manage backup "data/auth-before-diagnostics-$(date +%Y%m%d-%H%M%S).sqlite3"
systemctl stop respect-studio-auth
```

2. 上传新版服务端 ZIP，将包内 `respect-studio-auth/` 的内容覆盖到 `/www/wwwroot/respect-studio-auth/`。**保留 `data/`、`.venv/`、`deploy/runtime.env`；不要删除原目录，也不要多套一层目录。** 不需要重建账号、Key 库或管理员。

3. 启动并检查：

```bash
cd /www/wwwroot/respect-studio-auth
systemctl restart respect-studio-auth
systemctl status respect-studio-auth --no-pager -l
curl -s http://127.0.0.1:8781/health
```

应返回版本 `1.9.0`。数据库新增诊断表自动完成，不需要新增 SQL 服务或修改反向代理。后台强制刷新后，每个账号有“请求诊断”按钮。

4. 客户端采集代码也需要打入新 EXE 后分发。**旧版 `2026.10.23.2` 不会上报客户端诊断。** 只更新服务端时，可以先看之后到达服务端的请求；客户端新功能尚未发布时看不到客户端日志是正常的。

## 保存和上报

- 客户端将元数据送入有上限的内存队列，由后台线程暂存到数据目录的 `usage-outbox.sqlite3`，与已有用量队列表分开。事件采集不等待磁盘或网络。
- 已登录时后台约每 5 秒尝试批量上报，单批最多 20 条；失败逐步退避到 5 分钟，不触发隐式登录续期。凭据失效后，完成下一次正常校验或重新登录再补报。
- 每条记录保留产生时的账号归属。未登录的失败登录尝试仅在同名账号之后成功登录时补报；从未成功登录的电脑无法上报这些本地记录。
- 客户端最多保留 7 天、2,000 条待上报记录，服务端最多保留 30 天、全站 50,000 条诊断。写入及上报时清理；服务端原有 `prune` 定时任务也会清理过期记录。达到上限删除最旧记录，因此不是永久审计凭证。
- 不记录密码、Key、令牌、请求/响应正文、提示词、素材、项目路径或带查询参数的 URL。目标只记录域名；服务端记录所见来源 IP，设备用不可逆摘要缩写显示。
- 队列满、进程退出、磁盘异常可能丢失部分诊断。后台显示服务端本次运行丢弃计数，以及客户端随成功上报携带的缺失计数。客户端报告属于客户端提供的信息，不能作为计费或授权依据。

## 怎么排查

| 看到的证据 | 可以判断什么 |
| --- | --- |
| 客户端 DNS / TLS / 连接错误，服务端无同编号记录 | 客户端未获得正常响应；需查本机、DNS、证书、代理及中间链路，不能只凭这一条定责 |
| 同编号服务端返回 401 / 403 | 请求已到达应用并被认证拒绝，不是单纯断网 |
| 同编号服务端也耗时很长 | 优先查服务处理、数据库及资源占用 |
| 服务端很快，客户端总耗时很长 | 再查代理、传输、客户端读取等阶段，不能直接把差值叫“网络耗时” |
| 本地补全依赖或预览耗时长，附近没有认证请求 | 优先查本地计算、共享盘读写；不是每个本地操作都要远程校验 |
| LLM 返回 HTTP 401 | 该 LLM 请求被目标服务拒绝认证，应核对对应配置，不能推断登录账号失效 |

这些记录用于从升级后积累证据，不能恢复升级前已丢失的详细请求，也不能实时看到断网电脑上尚未上报的记录。
